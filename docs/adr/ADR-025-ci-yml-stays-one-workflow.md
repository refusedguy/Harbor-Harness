# ADR-025: `ci.yml` не делится на `workflow_call`. Второго вызывающего нет, восемь required checks переименуются

> **Status (2026-11-17):** dated record, not normative. Числа сняты на `origin/dev` =
> `03a239ba`. Решение зафиксировано по issue #2194. Ни один workflow-файл, ruleset
> или гейт этим PR не меняется. Это снимок дерева на дату, а не утверждение о
> будущем, поэтому здесь нет баннера `Status: normative`.

- Дата: 2026-11-17
- Источник: issue [#2194](https://github.com/refusedguy/Harbor-Harness/issues/2194);
  полное измерение в [WORKFLOW_GENERATION.md](../WORKFLOW_GENERATION.md) §8 и §9.
- Затрагивает: только этот ADR и индекс [DECISIONS.md](DECISIONS.md).

## §1. Вопрос и вердикт

Отчёт по #2185 сравнил три способа работы с 17 workflow-файлами: генерацию в
fallout, свой генератор в сборщике и «списки плюс composite actions». Четвёртый
вариант из задания владельца в сравнении отсутствовал: разбить `ci.yml` на
несколько workflow'ев, вызываемых через `workflow_call`. Issue #2194 потребовал
разобрать его отдельно.

Вердикт: **не разбивать**. У reusable workflow нет второго вызывающего, а
перенос джобов переименовывает все восемь обязательных проверок разом. Решение
не меняет `.github/workflows/**`, `.github/rulesets/**` и гейты.

## §2. Почему нужен второй вызывающий

`workflow_call` платят за переиспользование. Выигрыш появляется, когда одну и ту
же работу вызывают из двух мест. Замер в §8.4 отчёта и проверка на `03a239ba`
дают одно и то же:

| Что | Замер |
|---|---|
| workflow-файлов | 17 |
| Триггеров `on.workflow_call` | 0. Единственное совпадение строки `workflow_call` под `.github/workflows/` это комментарий в `.github/workflows/test-os.yml` |
| Вызывающих у каждого файла | один |

Дублирования, которое устранял бы reusable workflow, в дереве нет.

Одно исключение уже описано в самом workflow. Джоб `changes` файла
`.github/workflows/test-os.yml` намеренно повторяет фильтр `ci.yml::changes`.
Комментарий над ним объясняет выбор: workflow не может прочитать выходы другого
workflow, поэтому доступны только reusable workflow и дублированный фильтр, а
дублированный фильтр это меньшее изменение. Измерение §8.4 уточняет цену: 16
записей пути в `test-os.yml`, и все 16 присутствуют в списке `dotnet` файла
`ci.yml`. Список `test-os.yml` строгое подмножество, уникальных записей ноль.

Шестнадцать строк списка дешевле закрыть источником данных или composite
action. Оба приёма уже работают в дереве и не трогают имена джобов.

## §3. Что ломается в required checks

Восемь имен, которые требуют ruleset'ы, это значения `name:` под джобами.

| Required check | Файл |
|---|---|
| `gate` | `.github/workflows/ci.yml` |
| `public-api freeze` | `.github/workflows/ci.yml` |
| `checker self-test` | `.github/workflows/docs.yml` |
| `internal links` | `.github/workflows/docs.yml` |
| `markdown lint` | `.github/workflows/docs.yml` |
| `normative citations` | `.github/workflows/docs.yml` |
| `tree gates` | `.github/workflows/docs.yml` |
| `test project coverage` | `.github/workflows/docs.yml` |

Проверка на `03a239ba`: все восемь строк `name:` на месте, и все восемь имен
присутствуют как `context` в `.github/rulesets/dev.json` и
`.github/rulesets/master.json`.

Два свойства GitHub превращают разбиение в смену всех восьми имён сразу.

1. Джоб внутри reusable workflow сообщает результат как `<вызывающий джоб> / <вызываемый джоб>`. Форма приведена в обсуждениях GitHub #46752 и #72708, вложенные вызовы дают `CI / CI / Commit Validator`.
2. Reusable workflow нельзя выбрать обязательной проверкой ruleset'а, только вызывающий. Основание приведено в обсуждении #170628: такой workflow не запускается сам и не создаёт отдельной записи проверки.

После переноса джоба в вызываемый файл проверка `gate` станет называться
`<вызывающий> / gate`, и так далее для всех восьми. В тот же PR придётся править
оба ruleset'а, а также настройки защиты ветки в GitHub. Иначе правило ждёт
имена, которых больше нет. В `master` это усугубляется строгой политикой:
`strict_required_status_checks_policy` равен `true`, и head ветки должен
проходить все проверки. В `dev` тот же флаг равен `false`.

В задании отмечено, что переименование одного джоба уже стоило заблокированного
PR. Разбиение делает такое переименование восемь раз в одном изменении.

## §4. Что GitHub не пропускает через границу вызова

Правила перечислены в §8.1 отчёта со ссылками на документацию GitHub. `env`
уровня workflow не переносится ни в одну сторону. Секреты доходят только до
непосредственно вызываемого workflow. Права `GITHUB_TOKEN` во вложенных
workflow могут только сужаться. Записи `GITHUB_ENV` вызывающего не видны шагам
вызываемого. У джоба-вызова разрешены только `name`, `uses`, `with`, `secrets`,
`strategy`, `needs`, `if`, `concurrency`, `permissions` и `cache-mode`.

Измерение §8.2 считает, что на нашем корпусе пришлось бы объявлять на границе:
10 различных наборов per-job `permissions`, из них 8 джобов просят WRITE,
36 блоков `env:` уровня workflow, 2 ссылки на секрет, 7 джобов с `outputs:`.
Артефакты общие для прогона, поэтому цепочка `build` к `test`, `pack` и
`perf-gate` пережила бы разбиение. Граф `needs` вызывающего воспроизводится, но
внутренние джобы вызываемого не могут зависеть от джобов вызывающего.

Итог тот же, что в §8.2 отчёта: структура переносится, контекст не переносится.

## §5. Условия, при которых вердикт можно пересмотреть

Вариант становится возможным, когда выполнены все условия.

1. Появился второй вызывающий того же workflow с совместимым графом джобов. Один фильтр `changes` таким вызывающим не считается: он стоит 16 строк и закрывается без смены имён проверок.
2. Гейт из issue #2191, который сверяет имена обязательных проверок с именами джобов, уже работает. Сейчас такого гейта в `tools/gates/` нет, и расхождение ruleset'а с джобами никто не ловит до блокировки PR.
3. Переименование восьми проверок спланировано как одно изменение: оба ruleset'а в репозитории и настройки защиты ветки в GitHub меняются в том же PR, что и workflow'ы. Порядок и окно, в котором правило ждёт новые имена, должны быть заранее описаны. Использовать bypass-актора для этого окна или нет, решает владелец.
4. `env`, `secrets`, `permissions` и `outputs` объявлены на границе вызова и пересчитаны по дереву на момент изменения, а не по старому измерению.
5. CI зелёный, и все восемь проверок сообщаются под новыми именами. До этого момента вариант остаётся отклонённым.

## §6. Что делать вместо разбиения

Делить надо списки и шаги, а не workflow-файлы. Списки живут в данных, например
`tools/ci-project-lists.json` с нарезкой в `tools/ci-shard-slices.py`. Шаги
живут в composite actions, например `.github/actions/queue-wait`. Оба приёма
уже применены в дереве и сохраняют имена джобов, а значит, не трогают
обязательные проверки.

## §7. Что не входит в это решение

- Фактического разбиения `ci.yml` нет. Ни один файл под `.github/workflows/**` не изменён.
- Гейт, сверяющий восемь required checks с именами джобов, остаётся отдельной работой в issue #2191. Этот ADR только называет его как условие пересмотра.
- ruleset'ы `dev.json` и `master.json` не изменены. Имена в них совпадают с текущими джобами.
