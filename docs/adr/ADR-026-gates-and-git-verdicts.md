# ADR-026: батчинг вызовов git, а не замена git

## §1. Вопрос и граница решения

Вопрос «обязаны ли гейты использовать git» распался на два разных:

1. **Кто реально читает историю**, а не только индекс.
2. **Где теряется время**: в вызовах git или в собственной работе гейтов.

Ответ на первый: историю читают ровно три гейта. Всё остальное вызывает
`git ls-files`, то есть читает индекс за 4–25 мс на гейт. Ответ на второй: из
~55 с, проведённых набором внутри git, 53 с (96 %) приходятся на два гейта.

Здесь исследование заканчивается и начинается решение: какие из популярных
идей («взять библиотеку», «сделать shallow», «написать свой blame», «добавить
параллелизма») реально дают выигрыш, а какие только выглядят им.

## §2. Что измерено

### §2.1 Три гейта читают историю

| гейт | git-процессов на прогон | времени внутри git | wall гейта | что нужно от git |
|---|---:|---:|---:|---|
| `check-doc-cites.py` | 37 | 23.41 с | 60.3 с (74.4 с с шимом) | `git log -p` на 35 файлов + **29 фолбэков `git blame`** (17.96 с) + `cat-file --batch` (2.90 с) |
| `check-local-merge-loss.py` | 1546 | 30.95 с | 24.0–87 с | **944 × `git show`** (15.38 с), 498 × `git diff` (9.47 с), 9 × `git log` (4.63 с), `merge-base`/`cat-file -e`/`rev-parse` |
| `check-public-api-resign.py` | 35 | ~0.5 с | 1.47 с (30 коммитов) | `git log` списка коммитов, `git show` на коммит, `cat-file -e` на baseline |

Сумма внутри git по всему набору составляет **~55 с**, из них **53 с (96 %)**
в первых двух строках. Все остальные гейты тратят на git меньше секунды.
Fork+exec git стоит ~1.2 мс, инициализация репозитория ещё ~1.3 мс. 900 процессов
дают ~3–4 с чистого оверхеда до любой полезной работы.

### §2.2 Чтение объектов уже на парите

800 блобов, свежий клон, тёплый кэш:

| способ | блобов/с | МБ/с |
|---|---:|---:|
| `git cat-file --batch` (один процесс) | 1860–2272 | **24–29** |
| свой Go-ридер packfile (mmap + `.idx` + delta) | **1967–2086** | **25.4–27.0** |
| go-git v5.19.3, дерево + блоб | 1438–1744 | 18.6–22.6 |
| go-git v5.19.3, чтение по хешу | 1084–1266 | 14–16 |

Свой ридер проверен на побайтовость: 200 блобов, 0 расхождений по SHA-256
содержимого против `git cat-file --batch`. Узкое место в zlib и delta-разрешении,
они одинаковы у всех реализаций. Библиотека здесь не даёт ничего.

### §2.3 Батчинг бьёт параллелизм

Ровно то, что делает `check-local-merge-loss`: 944 чтения объектов.

| способ | время | против последовательного |
|---|---:|---:|
| 944 × `git show`, последовательно | 14.6–15.4 с | 1× |
| 4 процесса параллельно | 5.0–5.3 с | 2.8–3.0× |
| 8 процессов параллельно | 4.1–5.4 с | 2.8–3.6× |
| 16 процессов параллельно | 3.5–4.2 с | 3.5–4.4× |
| **один `git cat-file --batch`** | **0.51–0.58 с** | **25–30×** |

Параллелизм даёт 3–4× и упирается в ядра. На загруженной машине 8 потоков
показывали меньше, чем 4. Батчинг одним процессом убирает и fork/exec, и
повторную инициализацию репозитория, и повторный обход дерева.

### §2.4 Blame: go-git медленнее и врёт

Три цитируемых файла, один и тот же вопрос и ожидаемый ответ:

| файл | строк | `git blame` | go-git | отношение | совпало | разошлось |
|---|---:|---:|---:|---:|---:|---:|
| `CompactionPolicyInvariantTests.cs` | 631 | 414 мс | 2257 мс | 5.4× | 576 | 0 |
| `DialogKeyParityTests.cs` | 286 | 234 мс | 1523 мс | 6.5× | 280 | 0 |
| `CachingSystemPromptBuilderTests.cs` | 319 | 334 мс | 10 441 мс | **31.3×** | 277 | **8** |

8 строк разошлись на переименовании: go-git ищет файл по тому же пути в
родительских коммитах и не отслеживает rename. Размер бинарника гейта с
подключённым go-git растёт с **2 666 620 до 7 020 668 байт** (+4.35 МБ,
+163 %). Отдельно: go-git v5.19.3 не открывает git-worktree, падая с
`object not found` там, где git находит объект.

### §2.5 Shallow даёт фальшивое ускорение

На depth-1 клоне `git blame` отвечает за **20 мс против 310 мс** (15× быстрее),
но приписывает **все строки граничному коммиту**: 1 уникальный коммит против 5
в полном репозитории. `git log -p` отдаёт 1 коммит вместо 5. Правило
TEST-CITE-DRIFT становится сравнением HEAD с самим собой и тихо слепнет.
`check-doc-cites.py` уже проверяет это (`repo_is_shallow` → `TEST-CITE-NO-HISTORY`),
а `docs.yml` намеренно ставит `fetch-depth: 0`.

Сам репозиторий исследования shallow не был: `git rev-parse --is-shallow-repository`
→ `false`, `git rev-list --count origin/dev` → 2899, файла `.git/shallow` нет.
`git fetch --unshallow` локально не нужен; речь именно о CI-checkout.

## §3. Вердикты: что НЕ делать

Эти семь пунктов зафиксированы, чтобы их не проверяли заново.

1. **Не подключать go-git.** Blame в 5.4–31.3 раза медленнее и врёт (8 из 285
   строк на переименовании), бинарь +4.35 МБ, worktree не открывается.
2. **Не делать shallow.** 15× по скорости blame и неверный ответ: 1 уникальный
   коммит вместо 5. `fetch-depth: 0` в `docs.yml` стоит намеренно.
3. **Не писать свой blame.** Это поиск по DAG с эвристиками переименований,
   copy-detection, moved-строк и `-w`; git реализует это десятилетиями.
   Выигрыш выглядит как «30 % быстрее», а оборачивается расхождением с git.
4. **Не брать gitoxide или libgit2.** `tools/build-gates.sh` собирает с
   `CGO_ENABLED=0`: бинарник обязан быть статическим. CGO/FFI ломает контракт,
   Rust-тулчейн в сборке гейта стал бы новой зависимостью CI. gitoxide не
   измерялся вовсе, вывод сделан по документации и по запрету CGO.
5. **Не начинать с параллелизма процессов.** 2.8–4.4× с потолком по ядрам;
   батчинг даёт 25–30× одним процессом.
6. **Не ждать выигрыша от Go на чтении объектов.** Уже парите: 25.4–27.0 МБ/с
   против 24–29 МБ/с у `cat-file --batch`.
7. **Не расширять список гейтов «просто потому, что git».** `git ls-files`
   читает индекс, 4–25 мс. Свой парсер `.git/index` сэкономил бы ~0.1 с на
   набор и добавил код, который читает формат git.

## §4. Вердикт: что делать

| гейт | решение | выигрыш | цена |
|---|---|---:|---|
| `check-local-merge-loss.py` | **Оставить git, батчить:** 944 `git show` → один `cat-file --batch`; 498 `git diff` → один diff на merge со всеми путями; 9 `git log` → один log на дерево; `merge-base`/`cat-file -e`/`rev-parse` → батч. Go-порт имеет смысл только если он всё равно делается | **21–28 с** (31 → ~3 с внутри git; wall 24–87 → 6–10 с) | 1–2 дня на Python, +1–2 дня при Go-порте |
| `check-doc-cites.py` | **Портировать в Go, но git для истории не трогать.** Из 60–74 с гейта git занимает 23.4 с (31 %), остальные ~40–50 с занимает собственная работа Python: чтение 1291 `.cs`, разбор markdown, регулярки | **45–55 с** (потолок Go-порта, не 60–74 с) | 4–7 дней |
| `check-public-api-resign.py` | **Оставить git.** 35 процессов × ~15 мс = 0.5 с. Go нужен только ради единого бинарника, не ради скорости | 0.3–0.5 с | в рамках порта агента C |
| остальные гейты | **Оставить как есть.** Индекс стоит 4–25 мс; `check-gate-policy.py` и `guard-triage.py` git не используют вовсе | 0 | 0 |

Два уточнения в рамках `check-doc-cites`, оба **после** Go-порта и отдельной
работой:

- 29 фолбэков `git blame` → точечный `git blame -L <строка>` на 88 цитируемых
  строках: 113 мс против ~619 мс на файл. Это ~8 с CPU git, но около 1 с по
  wall, так как фолбэки уже параллельны (8 потоков). Нужна сверка вывода на
  всех 35 файлах.
- Флаг `--diff-merges=first-parent` в команде `git log` стоит **+560 мс (1.5×)**
  ради файла, который всё равно уходит в фолбэк. Если фолбэк остаётся, флаг
  можно убрать после проверки на 35 файлах.

Реконструкция из `git log -p` воспроизводит HEAD только для **2 из 35** файлов;
применение merge-диффа меняет результат на те же 2 из 35. Батчинг #2090 на
этом дереве не работает: гейт всё равно откатывается в 29 `git blame`. Поэтому
«ускорить doc-cites батчингом git» не является решением.

Итог по набору из отчёта:

| | сейчас | после |
|---|---:|---:|
| набор §10.2 (117 с) | 117 с | ~62–72 с (Go-порт doc-cites) |
| + `check-local-merge-loss` (24–87 с) | 141–204 с | ~68–82 с |
| + `check-public-api-resign` (1.5 с) | 143–206 с | ~70–84 с |

Масштабирование тоже говорит за батчинг: сейчас 31 merge → 1546 вызовов
(≈50 на merge); через год это ~2000 вызовов при линейном росте.

## §5. Что осталось неизмеренным

- **Холодный кэш страниц.** Все числа получены на тёплом кэше. Первый прогон
  `cat-file --batch` на основном репозитории дал 11.7 с против 0.42 с на
  тёплом (28×). На CI-раннере кэш холодный: перемерить в CI, прежде чем
  объявлять выигрыш.
- **Wall джобы `docs.yml`.** Гейты идут последовательно в одном джобе, сумма
  может отличаться от суммы гейтов.
- **PR-чекаут** (не `dev`): другой набор цитируемых файлов и merge'ей, значит
  другое число фолбэков.
- **arm64.** Бинарник собирается под обе архитектуры, замеры только на x64.
- **88 вызовов `git blame -L`.** Оценка сделана по одному замеру на одной строке.
- **Профиль `check-doc-cites` по функциям.** Оценка «40–50 с собственной
  работы» получена вычитанием, `cProfile` не гонялся.

Отдельная оговорка к чужим числам: в `docs/BENCHMARKS.md` §10.1/§10.2 есть две
неточности, которые этот ADR не исправляет (это задача
[#2132](https://github.com/refusedguy/Harbor-Harness/issues/2132)). Число
«37 git-процессов» относится к текущему `origin/dev`, а не к `a763c824`, где
батчинга ещё нет и гейт делает 600+ `git blame`. Сумма «117 с» не включает
минимум четыре настоящих гейта, включая `check-local-merge-loss` (24–87 с).
Сам замер неполон, см. [#2131](https://github.com/refusedguy/Harbor-Harness/issues/2131).
