# 17. Agentic product direction (внешнее ревью ChatGPT Astra, 2026-09-09)

> Источник: два раунда ревью от внешней модели (видела только дерево +
> наши уточнения). Статус: **принято как направление**, детали — в треках ниже.
> Принцип: evals сопровождают изменения с самого начала, а не после них.
> Связано: #19 (E2E/evals), #21 (two-process), #22 (v1.0), #27 (UI-миграция),
> #33 (слои), #36 (mouse grab), #37 (Evaluate-64), #38 (PTY flakes), #39 (hygiene).

## 0. Позиционирование (принято)

> Harbor превращает задачу в проверяемое изменение проекта: с планом,
> ограниченными полномочиями, тестами, понятным результатом и возможностью
> безопасно отказаться от изменений.

Не «ещё один агент с большим количеством tools», а система контролируемого
выполнения. Три направления из ревью зафиксированы так: **(1) надёжный
локальный coding agent — продукт; (3) общий runtime для TUI/IDE/desktop —
внутренняя архитектура; (2) платформа расширений — позже, по спросу.**

## 1. Три контура качества (разные проверки, не заменяют друг друга)

| Контур | Вопрос | Состояние |
|---|---|---|
| A. Корректность Harbor | Работает ли система по контракту? | Сильный: unit/integration/contract/arch/PTY/snapshots |
| B. Качество решения задач | Получает ли пользователь результат? | **Дыра**: нет evals-harness → трек §3 |
| C. Пользовательская завершённость | Может ли управлять результатом? | Частично → эпик §5 |

## 2. Evals: v0 сейчас, v1 на RunId (принята поправка ревьюера)

Baseline снимается ДО переделок, иначе не с чем сравнить. Инженерный
бэклог (§13 прошлого ревью) ≠ eval seed — не смешивать.

### Evals v0 (снаружи, без изменений runtime)
- Внешний раннер: fixture → запуск Harbor (CLI + `HARBOR_TUI=plain`,
  `MockLlmServer`) → timeout → независимая проверка → артефакты+метрики.
- Seed-набор (проверяем поведение, не сходство кода):
  1. мелкий логический баг; 2. null/empty edge; 3. фича в существующий API;
     4. многофайловое изменение по паттерну; 5. рефакторинг без смены поведения;
     6. сломанная сборка; 7. read-only диагностика; 8. запрет менять публичный API;
     9. работа поверх изменений пользователя; 10. противоречивая постановка.
- Отдельный набор runtime-resilience (cancellation, reconnect, crash, retries).
- Метрики: доля решённых; доля с соблюдёнными ограничениями; доля ложных
  успехов; вмешательства; **полная стоимость получения успеха**
  (все попытки / число успехов, не путать со стоимостью успешной попытки);
  время; классификация неудач (11 классов из ревью — в issue).
- Анти-самообман: проверяющий контур отделён от решающего; verdict выносит
  проверяющий, не transcript; повторы видимы (все попытки + стоимость);
  условия сравнения фиксируются (версия, модель, fixture, лимиты, дата).

### Evals v1 (на RunId, после минимального Run)
Тот же набор + RunId, сохранённые результаты, точные статусы, бюджеты,
recovery-сценарии, workspace artifacts.

## 3. Три измерения вместо одного статуса (принято как требование)

Выполнение (queued/running/awaiting approval/completed/failed/cancelled/
interrupted) × Проверки (not run/running/passed/failed/inconclusive) ×
Принятие (n/a, pending/accepted/rejected/conflict). Один `Success` всё это
скрывает — запрещено. «Verified» = «прошли команды X,Y на ревизии Z в
окружении W», не доказательство правильности; patch после тестов =
перепроверка.

## 4. Потоки (согласованные, не последовательные A→B→C)

- **Поток A. Закрыть миграцию** (#27 по собственным критериям +
  #33-ядро: AppState/AppMsg/AppReducer, zero-dep Engine). Критерий: миграция
  закончена, а не переименована. Таблица владения состоянием обязательна:
  один факт — один владелец (runtime: статус/approval/история/стоимость;
  клиент: сессия в окне/скролл/фокус). Спорные: steering-очередь,
  retry-countdown, ctx% из трёх источников.
- **Поток B. Evals v0 параллельно с A** (спецификация запрошена у ревьюера).
  Критерий: можно сказать, где текущий Harbor силён, где ошибается.
- **Поток C. Минимальный Run** (RunId, lifecycle, итог+reason, artifacts,
  cancellation, timeout, базовые бюджеты). Вертикальными срезами
  B1 (наблюдаемый) → B2 (ограничиваемый) → B3 (изменения+проверки) →
  B4 (честное восстановление) → B5 (дерево выполнения). Без универсального
  orchestration framework раньше первой пользы.
- **Поток D. Verified Change Workflow v1** (отдельный эпик, НЕ часть #27):
  контракт исходного workspace → изоляция → change set → проверки → отчёт →
  принятие/отклонение + конфликты. Worktree — основа, но контракт шире
  (§10 ревью: исходное состояние, перенос, acceptance).
- **Поток E. Recovery и управляемая автономность** — после рабочего D.
  Честность раньше удобства: неизвестный результат внешнего действия ≠
  отсутствие действия; никакого blind retry; exactly-once не обещаем.
  Таксономия tool safety запрошена у ревьюера (read-only/retryable/
  idempotency-key/compensable/verifiable + уровни дедупликации).

## 5. Бюджеты: точность важнее цифры (принято)

Разделять: usage провайдера / локальная оценка / тариф / неизвестно.
Жёсткий потолок честно: usage приходит после, параллельные запросы,
отмена не останавливает начисление. Учёт:
потрачено + зарезервировано + прогноз. Сначала политика остановки,
потом billing.

## 6. Дисциплинарные правила (в DEVELOPMENT.md, §7)

- Изменение архитектурной матрицы: только с обоснованием
  (ребро/почему/альтернатива/чувствительный доступ/постоянное vs временный
  exception с условием завершения). Матрица + код в одном коммите, иначе CI
  не ловит смысл.
- Retry/flaky: допустим только зарегистрированный (трек + гипотеза +
  first-pass виден + метрики); вечных флаков нет; concurrency-флак =
  подозрение на гонку в продукте, сначала опровергнуть.
- Goldens: обновление только с объяснением визуального изменения + до/после;
  не единственный барьер миграции (нужны семантические тесты:
  дедупликация повторов, чистое переключение сессий, disposal подписок,
  reconnect-контракт, гонка approval/cancellation).
- Live-model E2E — отдельный сигнал, не gate (провайдер/лимиты/детерминизм).
- Отчёт владельцу: результат → доказательства (команды, CI, до/после,
  regression test) → ограничения → изменения правил отдельным блоком →
  рекомендация + откат. Агент не формулирует критерии, не ослабляет проверки
  и не принимает свою работу единолично.

## 7. Плагины и безопасность (принято)

Заморозка расширения API (совместимость НЕ обещаем — «экспериментальный API»);
один exemplary plugin с тестами/lifecycle/секретами/reload. Capabilities —
политика и интерфейс, не песочница; формулировка только честная
(«доверенный код с полномочиями»). Модель угроз + проверки границ до
публичного remote. Sandbox-названия без enforcement — переименовать или
доделать.

## 8. Repo-hygiene:scope guard (принято с ограничением)

Чинить то, что приводит к ошибкам размещения, мешает миграции, двоит
источник правды, нарушает границы. Косметику и массовые переименования —
не в этап A (цена: устаревшие инструкции, битые ссылки, гигантские diff).
Чистка и поведение — раздельными коммитами. Детали — #39.

## 9. Не берём (явно)

- Схлопывание сборок ради числа (триггер — фича на 15 сборок, не ощущение).
- Унификация UI до пикселей; второй UI без спроса.
- Marketplace, рой агентов с параллельной записью, долговременная память,
  автовыбор дешёвой модели — всё после измеренного bottleneck.
- Массовый рефакторинг «до идеала» силами ИИ.
