## 0. Ответ в одной строке

**Боль есть, и она измерима: 61 конфликтный эпизод в workflow-файлах за одну ночь, в 2 файлах из 17; в остальных 15 конфликта не было никогда за всю историю репозитория.** Но перевод workflow-файлов в код **сам по себе не снимает ни одного из этих эпизодов**: конфликт двух агентов, правящих один и тот же workflow, просто переезжает из YAML в Go-файл или в F#. Снимают их четыре дешёвые правки, которые вместе убирают **59 из 61 эпизода (97 %)** примерно за 6–10 агент-часов.

**Проверено на нашем корпусе (не по описанию библиотек):** из пяти готовых вариантов, которые владелец назвал, **ни один не переживает наш корпус без потерь.** Generaptor (`regenerate`) жёстко падает на **11 файлах из 17** и молча теряет фильтры путей и входы `workflow_dispatch` ещё в 6; `Invex.StructuredText` — полное покрытие синтаксиса, но **0 скачиваний** у текущей версии и нет ни `regenerate`, ни `verify`; `github/gh-aw` — первоклассный проект GitHub, но его ценность для нас в одном файле (`github-workflow.json` из SchemaStore, 2 219 строк), и **эта схема проходит наш корпус на 100 %**, хотя дублей ключей не ловит; `github-ci-assembler` — 1 звезда, **без лицензии**, и он переименовывает джобы, что ломает восемь required checks; `github-action-parser` — 0 звёзд и последний коммит 15 месяцев назад.

**Что стоит взять как идею (бесплатно):** режим `verify` (запрет ручной правки) и режим `regenerate` (вывод модели из существующего YAML) как паттерн, и JSON-схему GitHub Actions как данные. **Что не стоит тащить:** ни одну из библиотек как зависимость.

**Пилот уже в дереве, и он это подтверждает.** Коммит `f02c2253` (#2202) перевёл `meas-jit-aot.yml` в модель на Go (`tools/gates/gen-workflows/`, 1 029 строк), и сгенерированный файл **побайтово равен** рукописному. Механизм работает, побайтовое равенство достижимо, зависимость не нужна. Но выбранный файл имеет **0 конфликтов за всю историю**, а обоснование пилота («два агента, правящие **разные** workflow, не пересекаются») описывает не ту боль, что измерена: наша боль — **два агента в одном и том же** workflow, и она переезжает в Go-файл без изменения.

## 1. Как это мерилось

Метод важнее чисел, поэтому он первый.

**Шаг 1 — переиграть каждое слияние.** В репозитории 570 merge-коммитов (все ветки, вся история), из них 276 — в ночном окне. Каждый переигран через `git merge-tree --write-tree <parent1> <parent2>`: настоящее трёхстороннее слияние, которое не трогает индекс и рабочее дерево, и печатает файлы, которые **несли бы конфликт**. Так найдено **766 записей «файл × слияние»** в ночном окне.

**Шаг 2 — достать сам конфликт.** Для каждого конфликтного workflow-файла взяты три версии (ours, theirs, merge-base) и выполнен `git merge-file -p --diff3`. Это даёт настоящие хунки с маркерами.

**Шаг 3 — классифицировать.** Для каждого хунка определены: контейнер (внутри какого ключа YAML он лежит), форма (обе стороны вставили в одну точку / обе стороны переписали один и тот же блок), тема (arm64-близнец, список шардов, пути кэша, …) и доля комментариев в теле конфликта.

**Шаг 4 — свести повторы.** 74 хунка сводятся в **61 различных эпизод** (один и тот же конфликт, повторённый на нескольких попытках слияния, считается один раз).

**Шаг 5 — проверить результат слияния.** Для всех 49 слияний, конфликтовавших в workflow-файле, взят **закоммиченный результат** и каждый workflow-файл в нём разобран загрузчиком YAML, который **отказывается читать маппинг с дублем ключа**. Так найдено, сколько конфликтов кончилось сломанным файлом (§5.3).

**Шаг 6 — проверить чужие инструменты на нашем корпусе.** Исходники `Generaptor` и форка `fallout` склонированы в `/mnt/projects/wt-conflict-study/` и `/mnt/projects/wt-fallout-study/`; набор поддерживаемых ключей взят **из исходников обратного отображения** (`Generaptor/ScriptGenerator.fs`), а не из README. Корпус разобран тем же скриптом, что и в шаге 3.

**Что этот метод не ловит.** Слияния, сделанные через `rebase` (ветка `backup/*-pre-rebase` в дереве есть), не оставляют merge-коммита и в выборку не попадают; см. §11.

Владелец спрашивает именно про workflow-файлы, и вот почему: **в бинаре и в таблицах конфликт — это шум** (пересборка бинаря и добавление строки таблицы), а в workflow-файлах конфликт — это **тишина**: сломанный файл не падает, а создаёт прогон с нулём джобов (§5). Доля мала, цена — самая высокая в дереве.

### 2.3 Вся история: конфликт в workflow-файлах — это не хроника, а одна ночь

| окно | записей «файл × слияние» | из них workflow | хунков в workflow | различных эпизодов |
|---|---:|---:|---:|---:|
| вся история (570 слияний) | 816 | 56 | 56 | 61 + 1 односторонняя |
| ночь 2026-10-21/22 (276 слияний) | 766 | 55 | 55 | 61 |

**55 из 56 конфликтов workflow-файлов за всю историю репозитория произошли за одну ночь.** До 2026-10-21 workflow-файлы конфликтовали за 52 недели жизни репозитория **один раз** — и этот единственный случай оказался **односторонней правкой**: в `benchmark.yml` 2026-09-29 (`add944954`, «Merge origin/dev into perf/eventbus-fastpath-394») версия ветки совпала с базой, `git merge-file` не находит в файле **ни одного текстового конфликта**, и это не конфликт двух агентов.

Это меняет вопрос. Проблема не «YAML написан руками». Проблема — **параллельная волна, в которой 108 PR сливаются за сутки, и каждый агент, добавляющий гейт, дописывает шаг в конец одного и того же списка шагов**.

### 2.5 «4 джоба из 62» — это свойство встроенной модели, а не механизма

Проверено по исходникам форка (`/mnt/projects/wt-fallout-study/Fallout`):

- `src/Fallout.Common/CI/GitHubActions/Configuration/GitHubActionsJob.cs` — у класса поля `Name`, `Image`, `RunsOnLabels`, `TimeoutMinutes`, `ConcurrencyGroup`, `EnvironmentName`, `EnvironmentUrl`, `ConcurrencyCancelInProgress`, `Steps`. **Ни `needs`, ни `if`, ни `permissions`, ни `strategy`, ни `outputs`, ни `env` на уровне джоба там нет.**
- `src/Fallout.Common/CI/GitHubActions/IConfigureGitHubActions.cs` — точка расширения. `GitHubActionsStepPipeline.cs` её документирует как «the per-job insertion surface handed to `IConfigureGitHubActions.ConfigureSteps`» — то есть **вставить шаг**, и всё.
- Обсуждение [nuke-build/nuke#1230](https://github.com/nuke-build/nuke/discussions/1230) (август 2023) действительно предлагает расширяемый вариант: автор пишет *«surely GitHub workflows can be represented with simple POCOs which are then serialized to YAML»* и показывает `[GithubActionsExtended(typeof(Factory))]` с собственными POCO и YamlDotNet. **Но:**
  - `GithubActionsExtended` **не реализован ни в NUKE, ни в форке fallout** (grep по обоим деревьям — ноль вхождений);
  - сам мейнтейнер NUKE отвечает на это обсуждение: *«If your goal is maximum configurability, you will end up with a C# DSL that resembles pipeline's YAML dialect. Does this provide more benefits than writing the pipeline directly? I'm doubtful about it.»*
  - автор идеи в том же треде пишет: *«Making it 100% bulletproof. I do not plan on making this in a way which prohibits the user from making a faulty pipeline definition»*.

**Вывод в одну строку: выражает 4 из 62 встроенная модель; механизм (свой POCO + свой writer) ограничений не имеет.** Но это не меняет §7: свой writer — это и есть «свой эмиттер на Go» в другой оболочке, с той же ценой и тем же нулевым выигрышем в конфликтах.

Есть работающий прецедент в самом форке: у fallout в собственном репозитории **3 workflow-файла из 7 генерируются, 4 — ручные** (`build/Build.CI.GitHubActions.cs` и соседние). Гибрид, а не полный перевод.

### 2.6 C#-путь против Go-пути

| | C#-путь (генератор в `build/_build/`) | Go-путь (генератор в `tools/gates/`) |
|---|---|---|

| **кто владеет результатом** | сборщик (`build/`), пересобирает и коммитит артефакт | скомпилированный гейт (`tools/bin/harbor-gates-linux-*`), пересобирает и коммитит артефакт |
| **кто пересобирает** | джоба `gates-binary` / билд-сборщик | `tools/build-gates.sh` + джоба `gates-binary` (сверяет байты, `tools/bin/SHA256SUMS`) |
| **кто ловит расхождение** | сверка в сборщике — **требует dotnet**; отдельный скомпилированный гейт нужен, чтобы дерево можно было проверить **до** сборки | **тот же скомпилированный гейт** `gen-workflows --check`: работает без dotnet, читает закоммиченный YAML и сравнивает |
| **побайтовая воспроизводимость** | требует `-Deterministic` и pinned toolchain | уже настроена: `CGO_ENABLED=0 go build -trimpath -ldflags="-buildid= -s -w" -buildvcs=false`, гейт `--check` и `--verify` |

| **риск для полосы** | ошибка в эмиттере ломает файл → прогон с **нулём джобов** | тот же риск, **плюс** бинарь гейтов в тех же коммитах: сломанный `tools/gates/**` роняет половину гейтов сразу |
| **кто отвечает за язык описания** | C#, вместе с NUKE/fallout | Go, **отдельным** от сборщика языком — второе описание CI в дереве |

**Вывод по путям.** C#-путь дешевле по зависимостям и естественнее по «кто владеет», но он **не может быть проверен без dotnet** — а значит, «дерево здорово» нельзя проверить до сборки, и гейт-сверка всё равно нужен отдельным скомпилированным инструментом (готовый прецедент в дереве — `gen-seam-graph --check`, Go, без dotnet). Go-путь даёт сверку бесплатно, но требует `vendor/`-дисциплины и держит второе описание CI в Go.

**Ни один из путей не меняет арифметику конфликтов.** Оба меняют носитель описания, а не структуру данных, в которой происходит конфликт.

### 2.7 Пилот: единственный измеренный пример перевода (он уже в дереве)

Пока я мерил, пилот владельца приземлился на `dev` — коммит `f02c2253` «ci(#2200): the workflow file becomes an artifact, and a gate says so» (#2202). Это **факт, а не проекция**, и он калибрует всё, что ниже.

| что | значение | где |
|---|---:|---|
| весь пакет `tools/gates/gen-workflows/` | **1 029 строк Go** | `main.go` 326, `selftest.go` 132, `workflows/meas_jit_aot.go` 155, `yamlout/document.go` 416 |

**Калибровка моей модели стоимости.** Модель §10.1 предсказывала для `meas-jit-aot.yml` **137 – 202 строки Go (середина 173)**. Факт — **155**. Модель попала в свою полосу, и теперь её полоса откалибрована одним измерением, а не нулём.

**Что пилот доказывает и что нет.**

- **Доказывает:** побайтовое равенство достижимо; эмиттер не растёт с числом файлов; зависимость не нужна; сверка `--check` делается скомпилированным гейтом, то есть **дерево проверяется без dotnet** — ровно то, чего не умеет C#-путь (§2.6).
- **Не доказывает и не чинит нашу боль.** Обоснование пилота — «two agents that edit **two different** workflows edit two different Go files, and their changes cannot overlap in a merge». Это верно, но **разные файлы и так не конфликтуют**: за всю историю конфликтовали только `ci.yml` и `docs.yml`. Наша измеренная боль — **два агента, правящие один и тот же workflow** (джоба `selftest` в `docs.yml`: 32 эпизода, 52 % боли). В Go-файле одного workflow этот конфликт **остаётся ровно тем же** — он переезжает из `docs.yml` в `docs.go`.
- **Выбранный файл — правильный по риску, но не по больу.** `meas-jit-aot.yml` — 91 строка, 0 конфликтов за всю историю, не гейт, не в списке required checks. Это верно как «дёшево ошибиться», но перевод файла с **0 конфликтов** не может дать выигрыша в конфликтах по построению.

Гипотезы владельца — проверены, каждая посчитана.

| **(б) блок `env:` у джобы сборки** | **1** | **1,6 %** | **НЕ ПОДТВЕРЖДЕНА.** Один хунк на 61 эпизод. Блок `env:` в `ci.yml` один, и он менялся один раз. |
| **(в) список путей кэша** | **9** | **14,8 %** | **ПОДТВЕРЖДЕНА, причина № 4.** Три отдельных конфликта из-за одного блока `HARBOR_BUILD_OUTPUT_CACHE_PATHS` (`ci.yml:842`). |

### 4.1 Самое горячее место — одна джоба

| джоба | эпизодов | доля | файл |
|---|---:|---:|---|
| **`selftest`** | **32** | **52,5 %** | `docs.yml` (26) + `ci.yml` (6) |
| `test` | 12 | 19,7 % | `ci.yml` |
| `build` | 12 | 19,7 % | `ci.yml` |
| `plugininventory` | 4 | 6,6 % | `docs.yml` |
| триггер `push` | 1 | 1,6 % | `ci.yml` |

**Половина всей боли — одна джоба `selftest` в `docs.yml`.** Её устройство: список шагов, в который **каждый новый гейт дописывает свой self-test** (`<гейт> --self-test`) с 4–8-строчным комментарием. Список один, точка вставки одна, гейтов — 31. Два агента, добавляющие гейты одновременно, конфликтуют **всегда** — потому что вставляют в одну и ту же точку.

Вторая по числу причина — **пары близнецов**: в `ci.yml` джоба `test` и в `docs.yml` джоба `plugininventory` содержат по три пары шагов (`X64` / `ARM64`), которые обязаны называться одинаково и отличаться только бинарём и `if:`. Любое переименование шага приходится делать **дважды**, и второй раз — в паре, где рядом стоит почти идентичный текст. Отсюда 6 конфликтов из-за регистра одного слова.

Третья — **списки**: шарды (`ci.yml`, `docs.yml`), пути кэша (`ci.yml:842`), фильтры путей триггеров (`ci.yml:115–122`).

### 4.2 Четыре причины, которых в списке гипотез не было

1. **Один и тот же конфликт повторяется на нескольких merge-попытках.** 74 хунка → 61 эпизод: 13 хунков — повторы. Ветку вливали в dev по 2–7 раз (максимум: `feat/gates-all` — 6, `fix/2064-coverage-registry` — 6, `ci/2100-compiled-tree` — 7). **Каждая повторная попытка стоит ещё одного merge-коммита.**
2. **В списке шагов self-test лежит и целый новый джоб.** Агент, добавляющий гейт, дописывает **и** шаг в `selftest`, **и** новый джоб в конец `jobs:` — это две точки вставки на один гейт.
3. **Агенты придумали обход.** Пять merge-коммитов в ночь называются `ci: the arm64 steps carry dev's exact names, so the merge is clean` — агент **заранее** переименовал свои шаги так, чтобы конфликта не было. Это уже обходной путь, придуманный в ночи; он работает, но он не записан ни в одном правиле.
4. **Комментарий — это 68 % тела конфликта.** Пример 8: 52 строки конфликта, из которых 4 содержательны.

## 5. Цена одного конфликта

### 5.1 Конфликт, который убил полосу

2026-10-21 коммит `e7479b9a` («14 гейтов переезжают в бинарь», #2115) добавил arm64-близнецов трём шагам джобы `test`. Ветка, влитая в dev, разрешила слияние **(`50c41deba`)** так, что близнец потерял маркер списка (`- name:`), и YAML прочитал его как **продолжение первого шага**, а не как второй элемент. В одном маппинге стало два `if:`, два `shell:` и два `run:`. GitHub не читает файл с дублем ключа — прогон создаётся с **нулём джобов** и падает как «This run likely failed because of a workflow file issue».

Замер на закоммиченном результате слияния (`ci.yml`, строки 2435–2443, `50c41deba`):

```yaml
      - name: Report test measurements (issue #618)
        if: always() && runner.arch == 'X64'
        shell: bash
        run: |
          tools/bin/harbor-gates-linux-x64 test-measurements ...

        if: always() && runner.arch == 'ARM64'      <-- нет "- " здесь
        shell: bash
        run: |
          tools/bin/harbor-gates-linux-arm64 test-measurements ...
```

| величина | значение |
|---|---:|
| прогонов `ci.yml` с **нулём джобов** за 2026-10-21 | **56** |
| из них на `dev` | 5 (прогоны `39627731779`, `39627783779`, `39631514354`, `39633471298`, `39637350343`) |
| окно, когда полоса `ci` на `dev` была мертва | **15:40 → 17:00 UTC** (≈ **63 минуты**) |
| остальные прогоны с нулём джобов | 51, на ветках, форкнутых до починки (до 19:00 UTC) |

Чистка комментариев **не снимает ни одного конфликта** (1 эпизод из 61 был «конфликт только в комментариях»). Она снимает **размер**: 67,7 % тела конфликта — проза. **Вывод по F5: не делать сейчас.** Это отдельная задача на 100+ агент-часов с риском потерять объяснения, ради 68 % читаемости конфликта.

### 6.2 Почему F1 — первая

F1 снимает **больше половины** боли и стоит **меньше всех** вместе взятых. Дополнительно: он убирает вторую точку вставки на гейт. Сегодня добавление гейта трогает 11 файлов, из них **два** — это список шагов в `docs.yml` и новая джоба в `docs.yml`. После F1 список шагов перестаёт быть рукописью.

**Побочный эффект F1, который стоит сказать:** комментарии к self-test-шагам (4–8 строк на гейт) переезжают в JSON. Это ровно то, что `docs/WORKFLOW_GENERATION.md` называет проблемой R7 («проза уезжает в C#»). Здесь проза уезжает **не в код, а в данные** — и остаётся рядом с тем, что описывает. Это дешевле и безопаснее, чем генератор файла.

## 8. Критерий решения

Критерий должен следовать из чисел, а не из вкуса. Вот он:

> **Переводить workflow-файл в код, если он даёт не меньше N конфликтных эпизодов на ночную волну И стоимость перевода не превышает M агент-часов.**
>
> **N = 5 эпизодов на волну** (≈ 8 % от 61, ≈ 1 конфликт на каждые 20 слитых PR) — ниже этого файл не является источником боли, и его перевод оплачивает себя только тем, что он делает с ним дальше.
>
> **M = 10 агент-часов** — это цена F1 + F2 + F3 + F4 вместе (6–10 ч по §6). Это порог, ниже которого перевод не может быть оправдан, потому что те же 59 эпизодов снимаются дешевле.

**Как N и M получены, а не выбраны.**

- **N = 5.** 61 эпизод на волну из 108 слитых PR — это 1 конфликт на 1,8 PR. Порог 5 эпизодов означает «файл даёт не меньше одного конфликта на каждые 20 PR». Ни один файл, кроме `ci.yml` (30) и `docs.yml` (31), к этому порогу не подходит — **порог отсекает 15 файлов из 17 сразу, по данным, а не по вкусу**.
- **M = 10.** Измерено: F1 — 2–3 ч, F2 — 2–4 ч, F3 — 1–2 ч, F4 — 0,5–1 ч. Сумма — 5,5–10 ч, то есть **верхняя граница 8–10 часов** — это ровно стоимость дешёвых правок. Любой перевод, который стоит больше, чем F1–F4 вместе, должен снимать больше, чем F1–F4 вместе.
- **Проверка критерия на своих же числах.** При N = 5 в перевод попадают 2 файла (`ci.yml`, `docs.yml`). При M = 10 перевод **не окупается ни для одного**: максимальный маргинальный выигрыш перевода поверх F1–F4 — **2 эпизода на волну** (те два, что не покрыты ни одной из правок) за 30–60 часов. То есть **правило, применённое к моим же числам, говорит «не переводить ни один файл»** — а F1–F4, которые стоят до 10 часов, снимают 59 из 61.

**Что изменило бы вердикт.** Три вещи, и все три — про **структуру**, а не про формат:

1. Если бы гейты описывались **по одному файлу на гейт** (а не по файлу на workflow), F1 стал бы частью генератора, и перевод начал бы снимать конфликты. Но это и есть F1, только дороже.
2. Если бы файлов было 62, а не 17, и каждый файл конфликтовал — тогда N отсекал бы меньше, и перевод окупался бы. У нас 15 файлов без единого конфликта.
3. Если бы ценой конфликта был не 63-минутный провал полосы, а час переписывания, — тогда лечили бы F1–F4, а не генератор. Но это верно и сейчас: **58 из 61 эпизодов не ломали ничего**, они просто съедали чтение и merge-попытки.

## 9. Что перевод в код даёт сверх дешёвых правок — и чего не даёт

### 9.1 Даёт

| что | насколько это ценно |
|---|---|
| **Правило «файл нельзя править руками»** (генератор + сверка в CI) | Ценно: сегодня рукописный `ci.yml` можно сломать, и ломают. **Это ровно то, что даёт режим `verify` у Generaptor** — и это единственное, что стоит взять из чужих библиотек: паттерн, а не пакет. Но это правило **уже можно купить дешевле** — гейт `check-workflows` ловит формы, которые ломают GitHub, за 1 072 строки Go и без генератора. |
| **Структурная корректность вывода** | Генератор не может выпустить YAML с дублем ключа. Ценно, но **уже куплено**: 56 мёртвых прогонов закрыты гейтом, а не генератором. |
| **Описание гейта и его вызов в одном месте** | Ценно по существу. Но F1 делает ровно то же для 80 % гейтов и на 300 строк вместо 13 000. |
| **Уход от YAML как формата** | Ценно теоретически. YAML-файлы здесь — не «плохой формат», а носитель 4 756 строк обоснований, которые YAML умеет хранить рядом с кодом и которые Go- или C#-литералы раскладывают по файлам. |
| **Рост файла перестаёт быть ростом файла** | `ci.yml` вырос с 282 строк (2026-09-01) до 3 520 (2026-10-22) — **×12,5 за 7,4 недели**; `docs.yml` — с 143 (2026-09-29) до 1 742 — **×12,2 за 3,3 недели**. Перевод этого не останавливает: файл вырастет так же, только медленнее и незаметнее. |
| **Готовая JSON-схема GitHub Actions** (из `gh-aw`) | Ценно и **не требует зависимости**: это файл данных. Она **проходит наш корпус на 100 %** (§2.4) и закрывает класс, который наш гейт не ловит: **неизвестный ключ** и **неверный тип**. Но этот класс в нашей истории **не кусался ни разу** (0 инцидентов из 61 эпизода), а дублей ключей схема не ловит вовсе. |

### 9.2 НЕ даёт

| что | почему |
|---|---|
| **Конфликт двух агентов, правящих один и тот же workflow** | **Остаётся — просто в Go- или F#-файле.** Все 61 эпизод — это «обе стороны вставили в одну точку одного и того же списка». В любом языке список шагов — это список, и вставка в его конец — та же самая точка. Перевод меняет расширение файла, а не геометрию конфликта. |
| **Читаемость при отладке** | **Падает.** Сегодня читатель открывает `ci.yml` и видит, что делает полоса. После перевода он должен открыть файл модели и пройти через эмиттер, чтобы понять, какой YAML получится. Для инцидента из §5.1 (близнец потерял `- `) это значит читать Go-файл, чтобы понять, почему YAML сломан. |
| **Второй язык описания CI** | **Появляется.** Описание CI перестаёт быть YAML и становится Go + YAML (эмиттер) + JSON (списки). Три представления одного. |
| **Точка отказа** | **Появляется.** Ошибка в эмиттере ломает файл целиком: полоса не падает, а исчезает (0 джобов) — тот же класс, что в §5.1, только теперь он в коде, который пишет код. Сейчас у этого класса есть гейт (`check-workflows`), который ловит его заранее; при генераторе к нему добавляется ещё один слой, в котором ошибка не видна ревьюеру diff'а. |
| **Число строк, которые надо поддерживать** | **Растёт.** 9 708 строк YAML → **10 912 – 14 636 строк Go** (плюс эмиттер, плюс гейт сверки, плюс self-test). |
| **Правило required checks** | Не помогает: `docs/WORKFLOW_GENERATION.md` §8.3 показывает, что разбиение на `workflow_call` переименовывает все восемь required checks. `gh-ci-assembler` переименовывает джобы **ещё и по своей схеме** (`build--drupal--docker-php`, имя `[stage] pkg-id · job-name`) — это блокер, а не косметика. |
| **Обоснование пилота как обоснование лекарства** | Пилот `gen-workflows` (§2.7) обоснован так: «two agents that edit **two different** workflows edit two different Go files, and their changes cannot overlap in a merge». Это верно, но **разные файлы и так не конфликтуют** — за всю историю конфликтовали только `ci.yml` и `docs.yml`. Лечится не «разные файлы», а **два агента в одном файле** — а этот конфликт переезжает в Go-файл того же workflow без изменения. |
| **Дешёвый вход через `regenerate`** | **Не работает на нашем корпусе.** `regenerate` — единственная идея, которая обещала «вывести модель из 9 708 строк автоматически». Проверено по исходникам: он **падает на 11 файлах из 17** и **молча теряет** фильтры путей (11 файлов) и входы `workflow_dispatch` (6 файлов). Автоматический вход есть только для 6 файлов, и даже для них он теряет данные. |

**Итог §9: перевод в код — это не средство от конфликтов. Это другой способ хранить то же самое, дороже и с худшей читаемостью.**

## 10. Стоимость перевода и окупаемость

### 10.1 Модель оценки (в документе, чтобы её можно было оспорить)

```
Go_lines(file) = (yaml + comment) * K + jobs * A + steps * B + OVERHEAD
    K        = 1.05 .. 1.35   (накладные расходы вложенных map/struct-литералов Go)
    A        = 2 .. 3          (поля структуры джоба)
    B        = 1 .. 2          (поля структуры шага)
    OVERHEAD = 40 .. 70        (функция describe(), импорты, проводка — на файл)
```

**Проекция в часах:** 1,5–3 коммита в час на механической транскрипции с итерацией до побайтового совпадения (калибровка: `tools/gates/gen-seam-graph` — 3 709 строк Go за 5 коммитов; `tools/gates/demo-repro` — 1 564 строки за 2 коммита; `tools/gates/check-workflows` — 1 072 строки). **Проекция**, но теперь **откалиброванная одним фактом**: пилот `gen-workflows` (§2.7) написал 155 строк Go на 91 строку YAML, и модель §10.1 дала для этого файла 137 – 202 — попадание.

**Общая часть уже оплачена.** Пилотом в дереве лежат 874 строки Go, которые не растут с числом файлов: эмиттер YAML (416), гейт `--check` с self-test (458). Для остальных 16 файлов нужны только **модели**, то есть числа колонки «Go (середина)» минус уже написанные 155.

### 10.3 Как меняется цена входа из-за `regenerate`

Обещание `regenerate` — «вывести модель из существующих YAML, а не писать её руками». Проверено на нашем корпусе:

| что | сколько | что это значит для цены входа |
|---|---:|---|
| файлов, на которых `regenerate` **падает** | **11 из 17** | для них модель всё равно пишется руками |
| файлов, на которых `regenerate` **проходит, но молча теряет** данные | **6 из 17** | `on.push.paths` / `paths-ignore` / `pull_request.paths` (11 файлов), `workflow_dispatch.inputs` (6 файлов) — **фильтры путей это ровно те списки, которые конфликтуют** |
| строк комментариев, которые `regenerate` **не может** восстановить | **4 756 (49 %)** | их надо либо писать руками в скрипте, либо выбросить |
| ключей, которых нет в обратном отображении и которые надо **дописать в библиотеку** (или в её форк) | 9 групп | `env:` корня, `outputs:`, `continue-on-error:`, `max-parallel`, `security-events`/`attestations`, `paths`/`paths-ignore`, `workflow_dispatch.inputs`, `matrix.include` (форма), права `permissions` сверх шести |

**Цена входа через `regenerate` не 0, а «цена F1 + цена починки библиотеки».** В нашем корпусе библиотеку надо расширять девятью группами, и каждая расширение — это и writer, и обратное отображение, и тест. На форке это **1 200 – 2 500 строк F#**, и потеря 4 756 строк комментариев всё равно необратима.

### 10.4 Окупаемость

| сценарий | конфликтов снято | строк | агент-часов | конфликтов на час | вердикт |
|---|---:|---:|---:|---:|---|
| **F1 + F2 + F3 + F4 + F6 (дешёвые правки)** | **59 из 61 (97 %)** | ≈ 600 Go + 450 JSON | **6 – 10** | **≈ 6,6** | **окупается** |
| Перевод `ci.yml` в код (поверх F1–F4) | **0** | 3 749 – 4 919 | 10 – 20 | **0** | **не окупается** |
| Перевод `docs.yml` в код (поверх F1–F4) | **0** | 1 967 – 2 621 | 5 – 10 | **0** | **не окупается** |
| Перевод всех 17 файлов (поверх F1–F4) | **0** | 10 912 – 14 636 | 30 – 60 | **0** | **не окупается** |
| Перевод всех 17 файлов (вместо F1–F4) | **0** | 10 912 – 14 636 | 30 – 60 | **0** | **не окупается** |
| Перевод через Generaptor (форк + 9 расширений) | **0** | ≈ 1 200 – 2 500 F# + 4 756 строк комментариев потеряно | 20 – 40 | **0** | **не окупается** |
| Перевод через Invex.StructuredText | **0** | ≈ 800 – 1 500 C# + 9 708 строк модели руками | 20 – 40 | **0** | **не окупается** |
| **Перевод остальных 16 файлов поверх уже оплаченного пилота** (874 строки общей части уже в дереве) | **0** | ≈ 9 700 – 14 000 строк Go (модели) | 25 – 55 | **0** | **не окупается** |
| Чистка комментариев (F5) | 0 | 0 | 100 – 200 | 0 | **не окупается** (убирает 68 % читаемости конфликта) |

**Строка «конфликтов снято = 0» — это не недооценка, а конструкция.** Перевод в код меняет носитель описания, но не меняет то, что список шагов — список, в который дописывают в конец. Конфликт возникает из **структуры данных** (один список, одна точка вставки, 31 писатель), а не из **формата файла**. Менять формат, не меняя структуру, — значит переписать ту же боль на другом языке.

**Если уж переводить — то переводить структуру, а не формат:** файл **на гейт** (не на workflow), с общим каркасом, который собирает шаги в YAML. Тогда 31 писатель перестают быть 31 писателем одного файла. Но это в точности F1, и F1 стоит 300 строк JSON и 200 строк Go.

## 11. Что осталось неизмеренным

1. **Слияния через `rebase`.** Они не оставляют merge-коммита и в свип не попали. Следы видны по сообщениям коммитов («the rebase ate the comment opener», `78b812be`) и по веткам `backup/*-pre-rebase`. **Их вклад не посчитан.**
2. **Конфликты, разрешённые вручную в интерфейсе GitHub** (кнопка «Resolve conflicts» на вебе). Они не оставляют коммита в локальном дереве, если PR был смержен через squash. Источник 11 прогонов `docs.yml` с нулём джобов на ветке `fix/2061b` 21.10 **не установлен**.
3. **Время в часах.** Все «агент-часы» — проекция по калибровке на существующих пакетах гейтов; единственный измеренный пример — пилот `gen-workflows` (§2.7, 155 строк Go на 91 строку YAML). Факта по остальным 16 файлам нет.
4. **Стоимость перевода в Go / C#** — модель §10.1, откалибрована одним измерением (§2.7). Факта по 16 остальным файлам нет.
5. **`scagogogo/github-action-parser` на нашем корпусе не проверялся.** Проверены только метаданные репозитория (0 звёзд, последний коммит 17.07.2025).
6. **`Invex.StructuredText` на нашем корпусе не проверялся.** Проверены метаданные пакета и полнота модели по README; обратного отображения у пакета нет по документации, но исходники не читались.
7. **Что будет, если конфликт решает не человек, а `-X ours` / `-X theirs`.** `git merge-tree` считает это конфликтом; человек считает это «решено». Сколько из 206 слияний было решено «с любой стороны» — не измерено.
8. **Прогоны, упавшие из-за workflow-файлов, вне 2026-10-08 … 2026-10-23.** API прогонов отдаёт максимум 1 000 записей на запрос; окно в 15 дней упирается в этот потолок для `ci.yml`, `docs.yml` и `codeql.yml`. Для 15-дневного окна цифры «56 и 13» — **полные** (все 56 лежат в одном дне, 2026-10-21), но для более широких окон потолок мешает.
9. **Вклад `docs/CI_GATES.md` и `tools/README.md` в боль владельца.** Они конфликтовали чаще, чем workflow-файлы (84 и 50 слияний против 49), но конфликт в строке таблицы стоит одного мерга, а конфликт в workflow-файле может убить полосу. **Веса не измерены.**
10. **Точный перечень непокрытых `ci-project-lists.json` списков** (12 эпизодов со списками шардов) — не составлен.

## 12. Как повторить измерение

```bash
# 1. Переиграть каждое слияние и выписать конфликтные файлы.
git log --all --merges --format="%H%x09%ad%x09%s" --date=iso > merges.tsv
while IFS=$'\t' read -r sha date subject; do
  LC_ALL=C git merge-tree --write-tree "$sha^1" "$sha^2" 2>/dev/null \
    | awk -v sha="$sha" '/^CONFLICT \(/ { sub(/^CONFLICT \([a-z\/]+\): Merge conflict in /, ""); print sha "\t" $0 }'
done < merges.tsv > conflicts.tsv

# 2. Достать тела конфликтов для workflow-файлов.
git merge-base "$sha^1" "$sha^2"
git show "$sha^1:$path" > ours; git show "$sha^2:$path" > theirs; git show "$base:$path" > base
git merge-file -p --diff3 ours base theirs > conflict

# 3. Мёртвые прогоны: у прогона с нулём джобов updated_at == created_at.
gh api "repos/refusedguy/Harbor-Harness/actions/workflows/ci.yml/runs?per_page=100&created=<from>..<to>" \
  --jq '.workflow_runs[] | [.created_at, .updated_at, .conclusion, .head_branch] | @tsv'

# 4. Проверка чужого инструмента на нашем корпусе: собрать множество ключей
#    из его исходников и сравнить с ключами наших файлов.
#    Generaptor: Generaptor/ScriptGenerator.fs, функции SerializeOn /
#    SerializeJobs / SerializeSteps / SerializePermissions / SerializeStrategy.
```
