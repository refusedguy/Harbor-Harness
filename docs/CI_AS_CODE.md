### 1.3 Доказательство побайтового равенства

Эталон — нынешний рукописный файл. Команда:

```
$ harbor-gates gen-workflows --write --repo /tmp/scratch
wrote .github/workflows/meas-jit-aot.yml
$ diff .github/workflows/meas-jit-aot.yml /tmp/scratch/.github/workflows/meas-jit-aot.yml
$ sha256sum .github/workflows/meas-jit-aot.yml /tmp/scratch/.github/workflows/meas-jit-aot.yml
11de853b49a38b3a90d9faef4c3506bb4208601782aee1790f9c5a3a7ab72ece  .github/workflows/meas-jit-aot.yml
11de853b49a38b3a90d9faef4c3506bb4208601782aee1790f9c5a3a7ab72ece  /tmp/scratch/.github/workflows/meas-jit-aot.yml
```

`diff` — пусто, хеши — равны. **Побайтовое равенство достигнуто с первой попытки**, без
исключений и без «почти».

Что это стоило в решениях:

| решение | почему так | а не иначе |
|---|---|---|
| скаляр несёт **стиль** (`Plain`/`Double`/`Single`/`Literal`), а не только значение | иначе эмиттер «нормализует» кавычки и первый же прогон даёт другой файл | файл в репозитории пишет `"10.0.x"` с кавычками, а `description: Attempts per task` без них; кавычка — это решение автора, и сверка должна быть сверкой двух деревьев, а не двух написаний |
| комментарии — **поле модели**, а не отдельный файл | 13 из 91 строк файла — комментарии; побайтовое равенство требует, чтобы они были в артефакте | отдельный «файл прозы» — это вторая рукопись рядом с первой, и её тоже пришлось бы сверять |
| пустые строки — **флаг у пары и у элемента** | в файле их 12, и они стоят в конкретных местах | эмиттер, который вставляет пустые строки по своему правилу, даст другой файл |
| порядок пар — **срез**, не карта | карта в Go перемешивает порядок при обходе, и сверка побайтово становится невозможной | `map[string]Node` в модели — это генератор, чей выход зависит от порядка обхода |

### 2.3 Где именно конфликтует

**Живое подтверждение.** Rebase этого PR на свежий `dev` (`ac8e5e63`) конфликтовал **в пяти
файлах из четырнадцати изменённых**: `docs/CI_GATES.md`, `tools/README.md`,
`tools/bin/SHA256SUMS` и оба бинаря гейтов, плюс `.github/workflows/docs.yml`. Это ровно тот
список из §2.1, и он получен не разбором, а настоящим merge-конфликтом. Правила разрешения —
те же, что требует репозиторий: новая строка таблицы **в конец**, бинарь пересобран из
слитого дерева.

По nature конфликта (все 46 sync-merge с конфликтом в workflow-файле):

| что конфликтует | пример | как это лечится генератором |
|---|---|---|
| **список шагов одной джобы** — два агента добавили шаг в одну и ту же джобу | `ci.yml`: шаг в джобу `test` | **не лечится**: два агента, правящие `ci.yml`, конфликтуют и в Go-файле |
| **список гейтов в джобе `selftest`** | `docs.yml`: новый гейт добавил свой шаг в конец | **не лечится** для того же файла |
| **общий блок в двух файлах сразу** (`docs/CI_GATES.md` + `tools/README.md` + `tools/gates/main.go` + бинарь) | добавление одного гейта трогает 11 файлов | **не лечится** генератором workflow: это другой класс |

### 2.4 Что происходит при слиянии на стороне GitHub

Отдельно измерено: **0 из 1 093** PR, слитых в `dev` через squash, конфликтовали **на
слиянии**. Причина: ветка агента отстаёт от `dev` (в проверенном примере — на 3 коммита), и
GitHub делает трёхстороннее слияние, которое оказывается чистым, потому что агенты правят
**разные** регионы.

**Вывод, который меняет рамку разговора:** конфликт workflow-файлов у нас **не случается при
слиянии PR**. Он случается **внутри ветки агента**, на шаге «влить `dev` в свою ветку» —
и там он разрешается агентом (или менеджером) вручную, после чего PR сливается чисто. Поэтому
в истории `dev` конфликтов нет, а боль есть. Метод, которым это измерено: `git merge-tree
--write-tree` на парах родителей каждого sync-merge (§2.1).

### 2.5 Сколько конфликтов останется, если YAML станет артефактом

| сценарий | конфликтов в `.github/workflows/**` останется | конфликтов в репозитории останется |
|---|---:|---:|
| сегодня | 52 | 213 |
| переведён только пилот (`meas-jit-aot.yml`) | **52** | 213 |
| переведены `ci.yml` + `docs.yml` (два горячих файла) | 1 | 162 |
| переведены все 17 | 0 | 162 |

То есть **максимум, который даёт перевод всех 17 файлов, — 52 конфликта из 213 (24 %)**.
Оставшиеся 161 — в таблицах, в бинаре и в `CHANGELOG.md`, и генератор workflow-файлов их
не касается.

И главное: **перевод не устраняет конфликт, а переносит его в Go-файл.** Два агента, правящие
`ci.yml`, конфликтуют в `workflows/ci.go` ровно так же, как конфликтовали в `ci.yml`; файл
не становится меньше — он больше по строкам (§7), и «область конфликта» не сжимается, а
переименовывается. Что реально меняется: **два агента, правящие РАЗНЫЕ workflow-ы, сегодня
конфликтуют только если правят общий `ci.yml`** — а это и есть 32 + 19 = 51 конфликт.

### 6.1 Условие, которое накладывает воспроизводимость бинаря

`tools/build-gates.sh` собирает так:

```
CGO_ENABLED=0 GOOS=linux GOARCH="$arch" GOFLAGS=-mod=mod \
  go build -trimpath -buildvcs=false -ldflags="-buildid= -s -w" -o "$out" .
```

`GOFLAGS=-mod=mod` означает: модуль скачивается из сети при сборке. **Побайтовая
воспроизводимость коммитированного бинаря при этом не гарантирована**: другой момент времени
загрузки модуля, другая версия прокси-сервера, другая сумма в `go.sum` — и джоба
`verify-committed` в `gates-binary.yml` уйдёт в красный на совершенно неизменённом дереве.

**Поэтому зависимость в `tools/gates/` допустима только так:**

1. `go.mod` получает `require`, `go.sum` — фиксированные хеши;
2. **`vendor/` коммитится в репозиторий**, а `build-gates.sh` переключается на
   `GOFLAGS=-mod=vendor`;
3. `tools/build-gates.sh --verify` (сборка дважды, сравнение байтов) остаётся зелёным.

Это добавляет к дереву `vendor/` (для YamlDotNet-подобной библиотеки — десятки мегабайт) и
требует изменения `build-gates.sh`, то есть **трёх файлов, которые сегодня конфликтуют чаще
всех** (§2.1: `tools/bin/SHA256SUMS` — 76, оба бинаря — по 76).

**Это и есть ответ на вопрос «стоит ли брать зависимость»: её цена — второе по частоте
место конфликтов в репозитории.**

   1 411 структурных строк YAML → ~1 900 строк Go. Область конфликта не сжимается.

2. **Workflow-файлы — не главный источник конфликтов.** 52 из 213 (24 %). Первые восемь
   мест — таблицы, манифест и бинарники. Генератор workflow-файлов их не касается.

3. **YAML перестаёт читаться глазами.** Диагностика «почему CI не стартовал» сегодня — это
   `git log` по YAML и чтение 3 520 строк. После перевода — это чтение Go-модели, плюс
   понимание, что эмиттер печатает по своим правилам. Для человека, который не знает Go,
   это **хуже**, а не лучше: раньше ответ был в YAML, который GitHub тоже читает.

4. **Появляется второй язык описания CI, и его надо знать.** Правило репозитория уже
   признаёт это: гейты — Go, продукт — C#. Три языка в одном описании CI (YAML, Go, C#) —
   это больше, чем сегодня.

5. **Генератор становится точкой отказа.** Ошибка в эмиттере = файл, который GitHub не
   читает = прогон с **0 джобов** и статусом `failure`, которого никто не видит. Это уже
   было дважды: прогоны 39627731779 и 39627783779 (#2115, #2146) — «the `ci` workflow stopped
   running at all». Генератор увеличивает этот класс риска, а не уменьшает: сейчас плохой
   YAML можно исправить, посмотрев на него.

6. **«YAML — артефакт» требует гейта-сверки, и он стоит времени на каждом прогоне.**
   Сверка сейчас стоит **миллисекунды** (один файл, 91 строка, без ввода-вывода кроме чтения).
   На 17 файлах с 9 731 строкой — тоже миллисекунды. Это не проблема. Проблема в том, что
   сверка **обязательна**: без неё артефакт разъезжается, и гейт нужен ещё и ещё.

7. **Если боль концентрируется в горячих местах, дешёвые точечные правки дают тот же
   эффект дешевле.** Боль наших конфликтов — не в workflow-файлах, а в добавлении гейта
   (11 файлов, из них `docs/CI_GATES.md`, `tools/README.md`, `tools/gates/main.go`, манифест и
   два бинаря). Это ровно то место, где уже есть работающий образец: `gen-seam-graph`
   (генерирует `docs/SEAM_GRAPH.md`, сверяет `--check`). **Расширение этого образца на
   таблицу гейтов и на `tools/README.md` бьёт по первым шести местам списка конфликтов
   дешевле, чем перевод 17 workflow-файлов.**

8. **Цена входа несимметрична в обе стороны.** Пилот сделал один файл за 1 029 строк Go.
   Перевод `ci.yml` и `docs.yml` — это ещё ~2 900 строк Go, и **до первого конфликта** в них
   мы не знаем, стал ли конфликт в `ci.yml` меньше. А он не станет: он переедет.

## 10. Кто должен владеть сгенерированным YAML

| вопрос | ответ | почему |
|---|---|---|
| **кто генерирует** | **гейт** (`tools/gates/gen-workflows`), а не сборщик | гейты собраны в **один** коммитированный бинарь, который работает там, где нет SDK и нет сборки (`tools/README.md`, `tools/gates/README.md`); сборщик (`build/_build.csproj`) работает только там, где есть .NET — то есть **не** в доки-полосе, которая обязана ловить расхождение |
| **кто сверяет (`--check`)** | тот же гейт, в джобе `workflows` полосы `docs` | сверка должна идти **до** того, как полоса упала: расхождение модели и YAML — это ошибка коммита, а не ошибка сборки |
| **кто поймает расхождение и за сколько** | `gen-workflows --check` в джобе `workflows` полосы `docs`; полоса `docs` стартует на каждом PR (с путями или без) — **в пределах минут** после пуша, ДО того, как `ci` упадёт | гейт не нужен ни SDK, ни артефактов сборки, поэтому он срабатывает и на том PR, который ломает сборку |
| **а если сборщик пересобрал и переписал YAML?** | он не должен этого делать: два владельца одного файла — это ровно тот конфликт, который мы и обсуждаем | если генератор всё-таки живёт в сборщике, то `build/` обязан **не** коммитить YAML: иначе он перепишет артефакт, и сверка в `docs` начнёт краснеть на каждом PR, где сборщик отработал |
| **что если `docs` не стартовал?** | `docs` — самая дешёвая полоса (без .NET), она стартует на каждом PR; `ci` — самая дорогая. Расхождение ловится в дешёвой полосе | по принципу, уже записанному в `check-workflows`: «a gate that lives inside the broken file disappears together with it» |

**Вывод по владению: генератор и сверка должны быть в одном месте, в одном бинаре, в самой
дешёвой полосе. Сборщик — не то место: он требует SDK, он в критическом пути `ci`, и его
результат (перезаписанный YAML) конфликтует с идеей «YAML — артефакт, который проверяют, а не
который переписывают».**

## 12. Честный вывод

**Стоит ли переводить дальше: только два файла, и только если владелец считает, что конфликт
в `ci.yml`/`docs.yml` дороже, чем новый язык в дереве. Мой вердикт — скорее нет, потому что
первый по числу конфликтов класс проблемы находится в таблицах и бинаре, и там уже есть
работающий образец (`gen-seam-graph`), который дешевле в 7,4 раза.**

Что пилот доказал наверняка:

1. Механика «YAML — артефакт, правит его Go-модель, гейт сверяет побайтово» **работает**,
   и работает в Go без единой внешней зависимости, в том же бинаре, что и остальные гейты.
2. **Побайтовое равенство достижимо** — 91 строка YAML, 155 строк Go-модели, ни одного
   расхождения.
3. **Ручная правка YAML ловится** — с номером строки и обеими версиями.
4. **Ни одна из 17 наших файлов не содержит ничего, что Go-модель выразить не может** —
   100 % конструкций покрыты, YAML-anchors в файлах отсутствуют.

Чего пилот не доказал и что стоит сказать прямо: **он не доказал, что это лечит конфликты**,
потому что в пилотном файле их ноль. А замер по репозиторию говорит, что 76 % конфликтов
находятся не там, где генератор мог бы помочь.

## 14. Связанное

- `tools/gates/gen-workflows/` — генератор и сверка; `tools/gates/gen-workflows/workflows/` — по
  одному файлу на workflow.
- `tools/gates/check-workflows/` — существующая страховка (1 072 строки), ловит формы, которые
  GitHub не прочитает.
- `tools/gates/gen-seam-graph/` — образец «сгенерированный артефакт + гейт-сверка», который
  стоит распространить на таблицы (шаг 3 §11).
- `.github/workflows/gates-binary.yml` — образец «CI сам коммитит сгенерированный артефакт»,
  и место, где конфликтует бинарь (76 + 76).
- `docs/CI_GATES.md` — таблица гейтов; её колонки «Workflow» и «Jobs» — карта «гейт → workflow →
  джоб», и она конфликтует чаще любого workflow-файла.
- `docs/WORKFLOW_GENERATION.md` — предыдущее исследование (переезд сборщика на fallout), с
  которым согласуются числа по выразимости встроенной модели.
