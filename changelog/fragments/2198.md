### #2129 — гейт потери содержимого спрашивает git 67 раз, а не 1547

**Что было.** `check-local-merge-loss` (гейт против потери содержимого при
squash-слиянии) читал историю git **1547 процессами `git`**: 944 `git show
<rev>:<path>`, 498 `git diff --unified=0 <base> <head> -- <path>`, 10 `git log
--first-parent -p -- <path>`, 33 `git rev-parse`, 31 `git cat-file -e`, 31
`git merge-base`. Процесс стоит дороже чтения, и гейт был вторым по времени
в наборе: 7.741 с из 44.1 с (19 %).

**Что стало.** 67 процессов на тот же ответ: **1 `git cat-file --batch`**,
**1 `git diff` на merge**, **1 `git log -p`** на все пути сразу, 31
`git merge-base`, 2 `git rev-parse`.

| было | стало |
|---|---|
| `git show` × 944 | `git cat-file --batch` × 1 (поток) |
| `git diff -- <path>` × 498 | `git diff` × 31 (по одному на merge) |
| `git log -p -- <path>` × 10 | `git log -p -- <paths…>` × 1 |
| `git rev-parse <sha>^` × 31 | из тела коммита, через тот же batch |
| `git cat-file -e` × 31 | из того же batch (слово `commit` в ответе) |
| `git merge-base` × 31 | 31 (у него нет пакетного режима) |

**Число процессов видно в логе гейта.** Гейт печатает в stderr строку

~1200 (по одному `git diff` и одному `git merge-base` на merge), а не

**Два решения, которые стоит назвать.**

1. **`--no-renames` в общем `git log -p`.** Без него git склеивает
   переименованный файл с его предком, и файл, о котором спрашивает гейт,
   читается как «переименован», а не как «строки сняты по одной». По одному
   пути склейки не происходит (в диффе один путь), поэтому флаг делает общий
   обход истории тем же ответом, что и обход по одному пути.
2. **Файл, удалённый merge'ем, и файл, сменивший тип.** Удалённый файл — одна
   секция с `deleted file mode`; сменивший тип — две секции (удаление старого
   типа и добавление нового), и он проверяется, обе секции читаются. Раньше
   это различал `git diff --name-status`; теперь различает сам разбор диффа.

**Кэш разбора истории между прогонами CI — оценка, не реализация.** Разбор
истории меняется только когда в `dev` приезжает новый merge: за 32 merge'а их
было. Кэш keyed by tip дал бы промах на каждом PR (tip у PR — его собственный
коммит), а кэш keyed by «последний merge в dev» пришлось бы продлевать
коммитами самого PR — а это ровно тот кусок, который решает, «снимал ли
кто-то строку нарочно». После батчинга гейт стоит 6.6 с из 44.1 с набора
(15 %), и кэш снял бы ещё ~6 с — при новом состоянии, новом ключе и новом
способе спрятать потерю. Плюс ровно тот риск, который issue #2100 уже
называл: кэш, скрывающий ошибку. **Не рекомендую**, пока гейт не станет
дороже остального набора; реализация — отдельной задачей.

**Что проверено, а что нет.** Проверено локально: `gofmt`, `go vet`,
`go build` (гейт `go-quality` зелёный), self-test гейта зелёный, побайтовое
совпадение вывода в трёх режимах и на пяти путях отказа, счётчик процессов
`git`, гейт на посаженном нарушении — красный (код 1), и зелёный, когда
строка возвращена. Не проверено локально: сборка и тесты .NET — только на CI
(локальный `dotnet` на этой машине запрещён, OOM).
