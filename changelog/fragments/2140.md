### #2100 — кэш выходов сборки больше не благословляет выходы проекта, который изменился

**Что осталось в самом инструменте.** `normalize-mtimes` (теперь скомпилированный гейт `tools/gates/normalize-mtimes`) штамповал ТЕКУЩИМ ВРЕМЕНЕМ каждый файл под `obj/` и `bin/`. Из этого следовало ровно то, чего кэш выходов сборки делать не должен: выходы проекта, чьи файлы изменились, выглядели свежее, чем дерево, из которого они собраны.

**Правило, которое теперь есть.** Выходы штампуются ТОЛЬКО для проектов, чьи файлы НЕ изменились. Выходы проекта, который изменился, кладутся ЗА дерево (на секунду раньше базового коммита), и MSBuild пересобирает этот проект. Изменённый файл обязан быть перекомпилирован, и ошибка компиляции в нём обязана быть видна: кэш выходов решает, что не нужно компилировать, и неверное решение прячет ошибку компиляции за зелёной сборкой.

Единица решения — каталог проекта: выходы лежат в `obj/` и `bin/` рядом с ним, и изменение любого файла этого каталога может изменить то, что проект компилирует. Тест намеренно грубый: проект, который на самом деле не изменился, будет пересобран (это секунды), а проект, который изменился, не будет пропущен никогда (это корректность).

**Что это закрывает.** Удалённый файл. Его пути уже нет в дереве, значит он больше не вход компиляции, и «новее выхода» ему взяться неоткуда: проект остаётся «актуальным», а в собранную сборку попадает старая сборка с удалённым типом. Переименование файла — тот же случай.

**Проверка.** `--self-test` гейта строит два проекта (изменившийся и не изменившийся) с восстановленными выходами и требует: выходы неизменившегося проекта — текущее время (MSBuild пропускает проект), выходы изменившегося — на секунду раньше базового коммита (MSBuild пересобирает проект), изменённый источник — на секунду позже выходов, неизменённый — на время базового коммита. В отчёт добавлен счётчик `outputs_stale` — сколько выходов положено за дерево.

**Чего этот PR не делает.** Страховку (гейт «полоса скомпилировала то дерево, которое ей дали») делает другой агент по #2139. Принятие из #2100 — «дерево с намеренной ошибкой компиляции в закэшированном проекте даёт красную полосу» — проверяется прогоном CI: локальный `dotnet` на этой машине запрещён (OOM).

### #2078 — скомпилированные гейты живут и работают ТОЛЬКО на линуксе

**Решение владельца, записанное как заявление.** Скомпилированные гейты — это линуксовые бинари, и их ровно два: `tools/bin/harbor-gates-linux-x64` и `tools/bin/harbor-gates-linux-arm64`. Ни windows, ни darwin сборки нет и не будет: бинарь лежит в дереве именно потому, что гейт должен срабатывать там, где нет ни SDK, ни сборки Harbor, ни python, а бинарь, который надо СОБРАТЬ на раннере, это правило ломает. Windows- и darwin-сборка — это ещё ~9 МБ закоммиченных бинарей, которые надо держать в шаге с каждым изменением исходников, ради двух отчётных панелей OS-полосы.

**Где гейты работают.** Джоб `build` и шарды `ci.yml` — линукс, и гейты работают там. **OS-полоса (`test-os.yml`, windows-latest и macos-latest) гейтов НЕ гоняет:** там стояли два отчётных шага (`test-measurements`, `test-skips`), которые печатали панель по TRX-файлам; они убраны (#2083), потому что цифры, которые цитирует `docs/BENCHMARKS.md`, берутся с линуховых шардов, а гейт на всех OS один и тот же.

**Что теперь ловится автоматически.** `tools/check-gate-policy.py` получил три правила:

| правило | что ловит |
|---|---|
| `POLICY-BINARY-NON-LINUX-RUNNER` | джоб на не-линуксовом раннере зовёт бинарь |
| `POLICY-BINARY-ARCH-TWIN-MISSING` | джоб может идти на арх, а бинаря этой арх не зовёт |
| `POLICY-STEP-DUPLICATE-KEY` | у шага один и тот же ключ дважды, а такой файл GitHub не запускает |

**Что нашлось при ревизии вызовов.** В `ci.yml` три шага шарда были написаны как ОДИН шаг с двумя блоками `run:` (по одному на x64 и на arm64). YAML не позволяет ключу повторяться в маппинге, и парсер workflow'ей GitHub ОТКАЗЫВАЕТСЯ на таком файле: «This run likely failed because of a workflow file issue», прогон падает за 0 с, и вся полоса `ci` лежит — сборка, шарды, pack, AOT publish, perf-гейт. Разбор через PyYAML этого не показывает: он молча берёт последнее значение. Теперь близнец — это ДВА шага, по одному на каждую архитектуру, и `POLICY-STEP-DUPLICATE-KEY` не даёт этому вернуться.

**Джоб `gates-binary` проверяет оба бинаря и манифест.** Раньше он пересобирал и сверял байты, но не сверял `tools/bin/SHA256SUMS` с тем, что лежит в дереве, и не доказывал, что два файла — это две РАЗНЫЕ архитектуры. Теперь: манифест называет ровно те два файла, что лежат в дереве, и его хэши — их хэши (`sha256sum -c`), а ELF-заголовок каждого бинаря объявляет свою архитектуру (e_machine 62 = x86-64, 183 = aarch64). Сборка и проверка — в обоих джобах.

**Проверено.** `tools/check-gate-policy.py` (51 строка таблицы; 23 посаженных дефекта, каждый поднял своё правило, чистое дерево осталось чистым), `tools/check-md-links.py`, `tools/md-lint.py`, `go vet`, `gofmt` — зелёные. Бинарь пересобран (`bash tools/build-gates.sh`), оба файла `tools/bin/*` в коммите.
