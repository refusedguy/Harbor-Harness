# The allocation census of the test tree

Issue #2136.

The wall census (`tools/gates/test-census`) knows how long every test took. It
cannot see MEMORY: a test that allocates 12 GiB and a test that allocates
12 KiB can both take 3 ms, and the difference between them is the difference
between a shard that needs 8 GB of RSS and a shard that needs 400 MB.

This pull request adds the instrument that answers the byte side of the same
question, at RUNTIME, for every test in every shard:

- `tests/AllocationCensus.cs` — a per-test probe, compiled into every test
  project, because TUnit's global `[BeforeEvery]` / `[AfterEvery]` hooks are
  discovered only in the compilation they are written in. It reports the
  EXACT per-thread bytes when the measurement window stayed on one thread and
  the process-wide upper bound when it did not, and it says which one it
  reported. It is off unless `HARBOR_ALLOC_CENSUS=1`, so a normal run pays
  nothing for it.
- `tests/Harbor.Architecture.Tests/TestTreeAllocationMeasurement.cs` — the
  stage breakdown, per test project: what the READ costs, what the STRIP
  costs, what the two line SPLITS cost, and what the IDIOM costs (the
  read -> join -> strip -> split every rule that walks a tree itself pays).
- `tools/gates/test-census` — reads the census lines out of the TRX and
  renders the ranking next to the wall ranking.

The census DISPATCH INPUT in `ci.yml` turns it on for a measurement run.

## The fixes this measurement found

The instrument was pointed at the architecture suite's tree-reading machinery,
which is where the tree's bytes go. Three places read the whole tree for
nothing, and each of them now asks a cheap necessary condition first, or rents
its buffer:

- `ApprovalGateWaiterRaceRules` — the scan copies the file, scans its method
  headers and runs two regular expressions over every method body, and both
  waiter patterns require the literal `WaitForDecisionAsync`.
- `ProcessEnvIsolationRule` — three questions were asked per line of every
  test project, each of them a regular expression or a comment-and-literal
  strip over a line that almost never holds the answer.
- `SourceCommentBlanker` — the strip allocated a buffer of its own per call,
  and the buffer is dead the moment the string is built.

Each of the three keeps the previous implementation next to the new one, and
each is proved over the LIVE TREE: the blanker by the existing
`CommentStripperEquivalenceTests` (byte for byte), the other two by parity
tests that compare the old and the new answer file by file and line by line.

The product tree is untouched.
