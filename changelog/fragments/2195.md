### #2194 — четвёртый вариант разобран: у reusable workflow'ей нет второго вызывающего, а восемь required checks они переименовывают разом

**Что было.** Отчёт по #2185 (`docs/WORKFLOW_GENERATION.md`) сравнил три способа разобраться с 17 workflow-файлами: генерация в fallout, свой генератор в сборщике и «списки + composite actions». Третий способ из задания владельца — **разбить `ci.yml` на несколько workflow'ев через `workflow_call`** — среди них не был. У него две границы, которых нет ни у одного из трёх: что GitHub разрешает переносить через эту границу и что делает правило required checks.

**Что измерено.**

| что | замер |
|---|---|
| ограничения GitHub | процитированы дословно: вложенность (десять уровней), лимит 50 вызовов на файл, workflow-level `env` через границу не переносится, секреты передаются только непосредственно вызываемому, права `GITHUB_TOKEN` через цепочку только уменьшаются, `GITHUB_ENV` вызывающего не виден шагам вызываемого, у джоба-вызова разрешены только `name`, `uses`, `with`, `secrets`, `strategy`, `needs`, `if`, `concurrency`, `permissions`, `cache-mode` |
| что переживает границу | 62 джоба, 10 различных наборов per-job `permissions`, 8 джобов просят WRITE, 36 блоков `env:`, 34 имени артефактов, 2 ссылки на секрет — всё посчитано по корпусу, а не предположено |
| блокер | джоб внутри reusable workflow сообщает проверку под именем `<вызывающий> / <вызываемый>` (обсуждения сообщества GitHub #46752, #72708), а сам reusable workflow **нельзя** выбрать обязательной проверкой в ruleset (#170628). Значит, разбиение `ci.yml` переименовывает **все восемь** required checks разом и правит оба ruleset'а в том же PR |
| где бы окупилось | фильтр `changes`, который `ci.yml` и `test-os.yml` дублируют намеренно — решение записано в тексте (`.github/workflows/test-os.yml:98`). Измерено: 16 записей путей у `test-os.yml`, и **все** они есть в списке `dotnet` файла `ci.yml`; ноль записей, уникальных для `test-os.yml`. Список строгое подмножество, риск разъезда односторонний |
| вердикт | 17 workflow-файлов, **0** триггеров `workflow_call`, каждый файл вызывается один раз. Механизм существует ради переиспользования, а второго вызывающего нет. Шестнадцать строк списка дешевле закрыть источником данных или composite action — оба приёма уже в дереве — и оба не трогают имена джобов |

**Перепроверка отчёта.** Всё в §3 отчёта воспроизвелось на следующем дереве (`dev` @ `7d86fd0c`), кроме трёх чисел; два исправлены в тексте, одно не воспроизводится вовсе.

|---|---|---|

| **74** места вызова гейтов | **68** реальных мест вызова | построчный пересчёт без строк-комментариев: остальные шесть — проза в комментариях |
| `all` вызывается **5** раз | **2** раза | три остальных упоминания — комментарии в `docs.yml` |

Воспроизвелось: 17 файлов / 9 656 строк / 62 джобы; 4 724 строки комментариев; per-job `permissions:` 52, `if:` 20, `needs:` 18, `outputs:` 7, `strategy:` 5, `env:` 5; те же **4 из 62** джоба, выражаемые в модели fallout; 29 различных отображаемых имён джобов.

**Что добавлено.** Две величины, которых в отчёте не было: **минимальная YAML-обвязка**, переживающая любой вариант, — около **1 425 строк (15 % корпуса)**: блоки `on:`, имена джобов, права, граф `needs` и вызовы шагов; и **измеренный набор composite actions** — `setup-dotnet` (25 мест, 517 строк), `upload-artifact` (34 места, 856 строк), `run-gate` (72 места, 1 237 строк). Названо и то, что в composite action **не** переносится: три пары близнецов x64/arm64 в джобе `test` файла `ci.yml` (`.github/workflows/ci.yml:2711`), потому что близнец зовёт другой бинарь.
