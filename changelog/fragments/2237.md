### #2108, #2139 — гейт reference-trimmer различает полный и частичный прогон

**Что было.** Анализатор встроен в общую Compile (#2108), а кэш восстанавливает
`obj/` и `bin/`. MSBuild пропускает неизменившиеся проекты, и в лог попадают
finding только пересобранных проектов. Файлы
`_ReferenceTrimmer_DeclaredReferences.tsv` из кэша остаются, поэтому coverage
показывал 115 проектов при 3 finding в логе. Гейт сравнивал эти 3 с полным
baseline из 51 строки и выдавал десятки RT-STALE-BASELINE по строкам, которые
PR не трогал. На dev это дало run 44035167093, job 133878538425.

**Что стало.** Гейт считает число строк baseline, которых нет в разобранном
логе. Больше `partialStaleFloor` (8) означает частичный прогон: RT-STALE-BASELINE
не выдаётся, а печатается `partial compile, stale check skipped, N of M
findings`. RT-NEW-FINDING проверяется по тем finding, которые есть в логе.
Полный прогон остаётся строгим: одна забытая строка baseline даёт RT-STALE-BASELINE.

**Почему так.** Альтернатива, компилировать дерево целиком ради анализатора,
вернула бы примерно 260 с в PR-полосу, то есть цену, ради которой #2108
пересадил анализатор в общую Compile.

**Доказательства.** Self-test использует один baseline из 12 строк и два лога,
полный и частичный. Полный с мёртвой строкой красный, частичный с тем же
baseline зелёный, частичный с новым finding красный. На PR гейт зелёный:
115 проектов, 51 finding, 0 stale.
