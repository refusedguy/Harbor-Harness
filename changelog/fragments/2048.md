### #1734 — у плагина своя секция конфига, своя схема и форма, которую эта схема генерирует

**У плагина не было НИКАКОЙ конфигурации. `PluginContext.Configuration` — это был `IConfiguration` ХОСТА, поэтому плагин мог читать настройки хоста, но не мог сказать «у меня есть секция `plugins.web-search`», не мог объявить, какие у него настройки, и не мог опубликовать для них значения по умолчанию. Теперь у плагина есть своя секция, своя схема и форма, которую эта схема генерирует.**

**Схема — это данные, и лежат они рядом с плагином.** Плагин объявляет свои настройки в манифесте, и манифест читается ДО компиляции плагина, то есть хост знает, чего хочет плагин, ещё до того, как плагин запустился:

```json
{
  "name": "web-search",
  "config": {
    "endpoint": { "type": "string", "default": "https://api.example.com" },
    "maxResults": { "type": "integer", "default": 5, "minimum": 1, "maximum": 50 },
    "apiKey": { "type": "string", "secret": true }
  }
}
```

Значения пользователь пишет в своей секции общей конфигурации, `plugins.<plugin-id>`, и больше нигде. `JsonConfigStore` остаётся единственной точкой, где файл читается.

**Секция проверяется ДО старта плагина.** Регистратор разбирает секцию по схеме перед `IPlugin.Initialize`, поэтому плагин, чьи настройки конфигурация не удовлетворяет, просто не запускается: плагин, который стартовал с настройками, которые он не смог прочитать, падает потом, в месте, которое к ошибке отношения не имеет. Каждый отказ называет настройку, которая не так:

> plugins.web-search.prot: unknown setting 'prot'. The plugin declares: endpoint, maxResults, apiKey.

> plugins.web-search.maxResults: 100 is above the highest allowed value 50.

Настройку, которую пользователь не задал, плагин получает со значением по умолчанию из схемы: плагин читает значение и не знает, задавал его пользователь или нет. Настройка, для которой схема не публикует значения по умолчанию, ОБЯЗАТЕЛЬНА: плагин не стартует, пока пользователь не задал её.

**Форма.** `harbor plugin config <name>` печатает объявленное плагином, чтобы пользователю не приходилось угадывать форму секции:

```
Settings of 'web-search' (write them under plugins.web-search):
  endpoint  string  default: https://api.example.com  current: https://api.example.com
  maxResults  integer  range: 1..50  default: 5  current: 10
  apiKey  string  default: (required)  current: (secret)
```

**Где что лежит и почему.** Словарь (схема, настройка, значение, тип) живёт в `Harbor.Abstractions`, потому что `PluginContext.Config` отдаёт его плагину, а контрактная сборка заморожена, поэтому public-API база переподписана в том же коммите, что и исходники. Валидатор, читатель схемы и форма живут в `Harbor.Plugins.Abstractions`: плагиновые слои не могут дотянуться до конфигурационного семейства, поэтому проверка должна лежать там, где её видят и читатель манифеста, и регистратор. Секция хранится В СЫРОМ виде намеренно: что секция значит, решает схема плагина, а схема едет вместе с плагином; секция плагина, которого в этой сборке нет, всё равно переживает круг записи конфигурации, потому что это всё ещё настройка пользователя.

**Не проверено локально.** Сборка и тесты — только на CI: локальный `dotnet build` на этой машине запрещён (OOM).
