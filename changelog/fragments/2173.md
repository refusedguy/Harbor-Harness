### #2107 — кэш выходов сборки попадает, и дерево инкрементально: компиляция пересобирает 3 проекта из 117

**Что утверждал issue.** Кэш выходов сборки срабатывает, но компилируются все 117 проектов: дерево не инкрементально. Проблема сформулирована так: «MSBuild решает „проект актуален“ сравнением mtime», и из этого следовало, что «выходам и сгенерированным входам — РАЗНЫЕ mtime», и предписание: «штамповать только выходы файлов, которые не менялись».

**Что измерено (прогон 39723477934, PR `ci/2107-incremental`, дерево `dev` @ `bfa1c99d`).** Кэш попал (`…-bfa1c99d`, 1 841 МБ, 36.8 с), и компиляция пересобрала **3 проекта из 117**, а не 117.

| что | было | стало | чем измерено |
|---|---|---|---|
| проектов, пересобранных компиляцией | 117 из 117 | **3 из 117** | `obj/Release/net10.0/<T>.dll` новее начала компиляции = пересобран; шаг «DIAGNOSTIC: how many projects the compile rebuilt» |
| фаза компиляции NUKE, PR-полоса с кэшем | 247-260 с (замер issue) | **36.7 с** | `==> Compile: done (36663 ms)`, прогон 39723477934 |
| фаза компиляции NUKE, PR-полоса без кэша | 247-260 с (замер issue) | **190.8 с** (прогон 39718825965) / **219.8 с** (прогон 39721596368) | то же |
| фаза компиляции NUKE, пуш в dev с кэшем | — | 27.9-30.9 с (прогоны 39719387006, 39721963101) | то же |

Число пересобранных проектов — факт о диске, а не чтение лога: у проекта, который компиляция пересобрала, промежуточная сборка новее момента начала компиляции, а у пропущенного остаётся штамп восстановления.

**Три причины промаха кэша — и это три разные вещи.** Шаг восстановления печатает «Cache not found for input keys» во всех трёх случаях.

1. **Хеш props-файлов.** Ключ несёт хеш `Directory.Packages.props`, `Directory.Build.props`, `Directory.Build.targets` и `global.json`. PR, трогающий один из них, имеет префикс, для которого у базовой ветки нет записи. Замер: прогон 39718825965, префикс полосы `1de69dbd…`, базовой ветки `61e83d62…`. **Промах корректен и не покупается обратно**: `$(MSBuildAllProjects)` (все импортированные `.props`/`.targets`) — это ВХОД `CoreCompile`, поэтому изменившийся props-файл новее выходов, и каждый проект, который его импортирует, обязан быть скомпилирован заново.
2. **Список путей кэша.** ВЕРСИЯ кэша — хеш входа `path`, а восстановление просит у сервиса «запись с этим ключом И этой версией». Ветка, чей список отличается от списка базовой ветки, просит версию, которую базовая ветка никогда не писала. Замер: прогон 39721596368 (ветка `feat/gates-a`, в её списке `!tools/bin/**` и семь строк комментария, которых нет в списке `dev`): шаг разрешения назвал запись `dev` `…-6e6b0da9` (REST API перечисляет и область видимости, и версию), а восстановление её отвергло.
3. **Область видимости.** Сервис кэша отдаёт прогону записи его ветки, веток ниже неё и — для pull request — базовой ветки. Ручной запуск на ветке-фиче не видит записи `dev`. Прогон, который цитирует issue (39658451546), — именно такой: его шаг разрешения нашёл запись `dev` через REST API, а восстановление её не увидело. Правило сервиса, workflow его не меняет.

**Про предписание issue.** Оно требовало перенести restore перед штампованием. Замер говорит, что это не нужно: restore внутри компиляции — NO-OP, он не переписывает сгенерированные NuGet-файлы, а они (`obj/<T>.csproj.nuget.g.props`) входят в `$(MSBuildAllProjects)`; переписывание сделало бы все проекты устаревшими. Пересобрано три проекта, не 117.

**Про кандидата с `.pdb`.** В Release `.pdb` вообще не является выходом `CoreCompile`: `Directory.Build.props` задаёт `DebugType=none`, `_DebugSymbolsProduced` становится false, и файл уходит из списка выходов цели. Поэтому исключение `!**/*.pdb` из полезной нагрузки ничего не меняло (замер: в восстановленном дереве 2 файла `.pdb` под `obj/` и `bin/` из 23 во всём дереве, и сборка не производит ни одного).

**Хеш версии, посчитанный по исходникам `actions/cache`.** `getCacheVersion(paths, …)` — это SHA-256 строк пути (обрезанных, пустые выброшенные), соединённых `|`, плюс метод сжатия (`zstd-without-long` на образе прогона) и соль `1.0`. Для четырёх строк переменной: `c59a4786cc2123d53e9d1c95486e32a211f9dcf3885f53318b7aedde237d9947` — ровно та версия, которую REST API показывает для всех записей `dev`, написанных после #2117 (замер 2026-10-22, записи 9318303404, 9318108740, 9317538762).

**Что осталось красным.** Ничего не красное: полоса зелёная. Не сделано: (1) гейт, который бы ловил расхождение списка путей — с одной переменной расхождение невозможно, но правка самой переменной по-прежнему стоит полосе кэш до того, как базовая ветка запишет запись с новой версией; (2) страховка #2100/#2139 — это чужой заход; (3) локально не проверено: сборка и тесты .NET только на CI (локальный `dotnet` на этой машине запрещён, OOM).
