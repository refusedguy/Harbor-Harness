# Subagent brief — Harbor

The canonical brief for an agent working in this repository. Fill in `ISSUE` and send.

Do not restate the issue in the brief. The issue body already carries the
`file:line` evidence; repeating it crowds out the agent's own reading and it is a
known way to introduce a wrong claim into the task. Two of the briefs written by
hand before this file existed seeded two wrong claims that the agents had to
catch.

```
Task: fix issue #ISSUE in repo /mnt/projects/Harbor-Harness
(GitHub refusedguy/Harbor-Harness, base branch dev).

Read the issue body first — it carries the file:line evidence. Verify it
against current code before acting: it has drifted before. If the issue is
stale, say so and work from what the code is.

Measure before choosing an approach. Do not take a prescribed solution on
faith — if something is suggested, verify it is what this codebase needs.

## Where you work

    cd /mnt/projects/Harbor-Harness
    git fetch origin dev
    git worktree add .worktrees/ISSUE -b fix/ISSUE origin/dev
    cd .worktrees/ISSUE

Order matters: fetch FIRST, then create. A worktree created from a stale
origin/dev cannot be rescued by fetching afterwards — the branch is already
cut from the old ref.

Read and write only inside that worktree. Never /, ~, /home, /opt, /mnt
outside the repository. This box is shared, 7 GB RAM.

## Tools

- graft first: graft ask "<q>" --source, graft skeleton <file>,
  graft callers <symbol>, graft grep "<literal>". Exact spans, one read
  instead of six.
- rg/grep only with an explicit path — rg "p" src/ apps/, never from /.
- context7 for external library docs.
- No serena — ~220 MB language server per worktree, has crashed this box.
- If graft returns nothing, that is the answer. Say "not in the index"; do
  not widen the search.

## Rules

- No local dotnet. CI is the only verification.
- Conventional commit, --no-verify. TUnit only. Never delete or rename
  another contributor's tests — but a test that dies because the
  duplication it policed is gone is a correct outcome; name it and say why.
- A never-compiled file: read it end to end before pushing. No implicit
  usings here, and TUnit asserts are IsGreaterThan/IsEqualTo, not BeGreaterThan.
- git add -A picks up unrelated files. Check git status before committing.

## Done means

- PR against dev, title states what changed, body says what was wrong and why
  this fix rather than the obvious alternative. Include Fixes #ISSUE.
- Green CI. If a check goes red, fix it yourself — do not report back asking.
- Conflicts: rebase yourself. Never merge — that is mine.
- If it is a measurement, the measurement is the acceptance. If it is a
  guard, prove the guard is not vacuous, and mind what it scans: a guard
  over src/ cannot catch a problem in tests/.

## Report — short, in Russian

What was actually wrong. What you changed. What the test asserts and what
fails without it. What you deliberately did not do, one line each. No list
of candidates you considered and rejected.
```

## Why this file exists

The briefs written by hand before it were long, and length was the problem
rather than the solution. Three costs, all observed in one night:

- **Length crowds out judgement.** A brief that hands the agent a diagnosis
  removes the place where it would have formed its own. Twice a hand-written
  brief carried a claim the agent had to disprove — `Result.Of` for a
  `try/catch` rewrite, and a mis-attributed analyzer hit.
- **Duplicated evidence.** Issues already carry `file:line`. Restating them
  in the brief gave a second copy to drift out of sync with the first.
- **A report nobody reads.** Every agent produced a long list of candidates
  it considered and rejected. The rejections were worth something only when
  they changed a decision; the rest was noise in a monitor-facing channel.

What is in the brief is what an agent cannot infer: where it is allowed to
work, what it may not run, which tool answers questions best, and what
"done" means here.
