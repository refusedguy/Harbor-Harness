# coverage-registry — the product files the nightly coverage lane does not
# cover, and why each one is allowed to stay that way.
#
# OWNER: issue #1753. Read by tools/check-coverage-registry.py, on every
# nightly run.
#
# THIS IS A RATCHET, NOT A TARGET. The gate passes only when the set of
# files the measurement says are not covered is exactly the set written
# here:
#
#   * a hole this file does not carry is RED. A file that STOPPED BEING
#     COVERED fails, and so does a new file that was never covered.
#   * a row the tree no longer produces is RED. A file that got covered has
#     to have its row deleted in the same diff that covered it.
#
# So the file can only shrink, and the gate gets stricter as the tree is
# fixed. A covered file cannot stay blessed.
#
# ── FORMAT ────────────────────────────────────────────────────────────────
#
#   <path> | <kind> | <reason> | <owner>
#
#   path     The product file, repo-relative. A path that ends in "/" is a
#            PROJECT row: it accepts every product file under it.
#   kind     One of:
#              NEVER-RAN     the measurement saw the file and ran not one
#                            of its lines.
#              NOT-MEASURED  the file belongs to a project this lane does
#                            not load at all, so the measurement never saw
#                            it.
#   reason   Why this hole is allowed to stay. At least 40 characters, and
#            not a bare URL: a URL says where the debt is, not why it is
#            allowed here.
#   owner    A '@handle' somebody can be asked about.
#
# ── WHAT THE MEASUREMENT IS ──────────────────────────────────────────────
#
# The nightly lane's coverage job (issue #99, moved off the pull-request
# path by #1923) runs the twenty core+platform unit suites under the
# Microsoft.Testing.Platform coverage extension and writes one cobertura
# file per suite. The ui, e2e and load suites are NOT part of it: they are
# slow, they need a display, and their flakes (#423) would make the number
# unreadable.
#
# That scope is the reason this file is as long as it is. The lane's twenty
# suites do not reach the UI, the desktop app or the CLI, so every file
# they would have reached is a hole BY MEASUREMENT — not a claim that the
# code is untested in the repository as a whole. The rows say which of the
# two they are.
#
# ── WHY A FILE ROW AND NOT A PROJECT ROW ─────────────────────────────────
#
# A project row (a path that ends in "/") accepts every file under it, and
# it is used only where the lane is BLIND: a project no suite loads at all
# (the CLI and the Avalonia app). Everywhere else the lane does load the
# project, so it can see the difference between a file that is covered and
# one that is not — and a project row would hide that difference. Every
# file of a loaded project is therefore named on its own row.
#
# ── WHAT IS NOT HERE ─────────────────────────────────────────────────────
#
# The files the coverage engine reported NOTHING for, in a project it did
# report: they hold no code to cover (an interface, an enum, a global-using
# file, a source-generated context), so they are not holes and they are not
# listed. The report prints how many there were and cross-checks that none
# of them carries code.
#
# ── PROVENANCE ───────────────────────────────────────────────────────────
#
# Measured on run 39521931938 of the nightly workflow, on the branch
# ci/1753-per-file-coverage at 6f2b4987: 1250 product files, 497 of them
# covered, 581 holes — 373 the measurement saw and never ran, 208 in the
# two projects the lane does not load.
#
# The rows below are the measured state of the tree, not a wish list. A file
# that gets covered has to have its row deleted in the same diff that
# covered it, and a file that stops being covered has to have a row added
# in the same diff that dropped it.
#
