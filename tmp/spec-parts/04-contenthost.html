interface 1. IContentHost — рендер-агностичный контракт

Живет в Harbor.Ui.Framework (нулевая зависимость от Avalonia/UI-фреймворка). Предоставляет два члена:

  • object? ActiveView { get; } — текущий активный VM/view.
  • void NavigateTo(string route) — переключает активный контент по маршруту.
namespace Harbor.Ui.Framework.Navigation; /// <summary> /// Renderer-agnostic contract for the shell's active-content host. /// </summary> public interface IContentHost { object? ActiveView { get; } void NavigateTo(string route); }
Design note
Контракт специально минимален: ActiveView возвращает object, а не generic T, потому что разные рендеры могут привязывать его к ContentControl.Content (Avalonia/WPF) или к собственному пиксельному presenter'у (Spectre/Terminal).

impl 2. AvaloniaContentHost — текущая реализация

Файл: apps/Harbor.App.Avalonia/Navigation/AvaloniaContentHost.cs

Класс агрегирует все shell VMs в конструкторе, а NavigateTo делает switch по строковому маршруту. CommandPaletteViewModel исключён — см. раздел 7.

using System.Collections.ObjectModel; using CommunityToolkit.Mvvm.ComponentModel; using Microsoft.Extensions.DependencyInjection; using Harbor.Ui.Framework.Navigation; namespace Harbor.App.Avalonia.Navigation; /// <summary> /// Avalonia-specific content host. Resolves shell view-models from DI /// and exposes the currently active one through <see cref="IContentHost.ActiveView"/>. /// <para> /// <see cref="CommandPaletteViewModel"/> is intentionally omitted: it holds /// a direct <see cref="MainViewModel"/> dependency, so it stays lazy-resolved /// inside <see cref="MainViewModel"/> to avoid a DI cycle. /// </para> /// </summary> internal sealed class AvaloniaContentHost : IContentHost { [ObservableProperty] private ObservableObject? _activeView; public ChatViewModel Chat { get; } public SessionListViewModel Sessions { get; } public CodeEditorViewModel CodeEditor { get; } public DiffViewModel Diff { get; } public TokenUsageViewModel TokenUsage { get; } public ProviderBrowserViewModel ProviderBrowser { get; } public ProviderModelPickerViewModel ProviderModelPicker { get; } public SettingsViewModel Settings { get; } public FocusSessionViewModel FocusSession { get; } public BoardViewModel Board { get; } public AvaloniaContentHost( ChatViewModel chat, SessionListViewModel sessions, CodeEditorViewModel codeEditor, DiffViewModel diff, TokenUsageViewModel tokenUsage, ProviderBrowserViewModel providerBrowser, ProviderModelPickerViewModel providerModelPicker, SettingsViewModel settings, FocusSessionViewModel focusSession, BoardViewModel board) { Chat = chat; Sessions = sessions; CodeEditor = codeEditor; Diff = diff; TokenUsage = tokenUsage; ProviderBrowser = providerBrowser; ProviderModelPicker = providerModelPicker; Settings = settings; FocusSession = focusSession; Board = board; ActiveView = chat; } public void NavigateTo(string route) { ActiveView = route switch { "chat" => Chat, "sessions" => Sessions, "code" => CodeEditor, "diff" => Diff, "tokenUsage" => TokenUsage, "settings" => Settings, "board" => Board, _ => throw new NotSupportedException($"Route '{route}' is not supported by AvaloniaContentHost.") }; } }

DI 3. DI-регистрация (ViewModelRegistration)

Файл: apps/Harbor.App.Avalonia/Hosting/ViewModelRegistration.cs

Ключевые правила lifetimes:

  • Shell VMs (Main, CommandPalette, Board, Chat, SessionList, Settings, ProviderBrowser, ProviderModelPicker, CodeEditor, Diff) — Singleton.
  • TokenUsageViewModel — Singleton (MainViewModel пушит RecordUsage на каждый UiStore-тик).
  • OnboardingViewModel — Transient (сбрасывается при закрытии wizard).
  • FocusSessionViewModel — Singleton.
  • IContentHost — регистрируется перед MainViewModel, чтобы DI мог разрешить его конструктор.
internal static class ViewModelRegistration { public static void Register(IServiceCollection services) { services.AddViewModelLocator(); services.AddSingleton<ShellStatus>(); services.AddSingleton<OverlayController>(); services.AddSingleton<CostAnimator>(); // ContentHost aggregates shell VMs services.AddSingleton<IContentHost, AvaloniaContentHost>(); // Singleton cluster — shell VMs reference each other. services.AddSingleton<MainViewModel>(); services.AddSingleton<CommandPaletteViewModel>(); services.AddSingleton<BoardViewModel>(); services.AddSingleton<ProviderBrowserViewModel>(); services.AddSingleton<ProviderModelPickerViewModel>(); services.AddSingleton<SettingsViewModel>(); services.AddSingleton<CodeEditorViewModel>(); services.AddSingleton<DiffViewModel>(); services.AddSingleton<TokenUsageViewModel>(); services.AddSingleton<FocusSessionViewModel>(); services.AddTransient<OnboardingViewModel>(); } }

XAML 5. 3 варианта XAML-миграции

Текущий MainWindow.axaml жестко прописывает каждую view и управляет IsVisible через EqualityConverter. Ниже — три стратегии, как упростить это.

Variant A Pass-through properties на ContentControl
ContentControl сам знает, какой VM показывать. Минимум изменений в XAML.
<!-- MainWindow.axaml --> <ContentControl Content="{Binding ActiveView}" DataContext="{Binding ActiveView}"> <ContentControl.ContentTemplate> <DataTemplate DataType="vm:ChatViewModel"> <views:ChatView /> </DataTemplate> <DataTemplate DataType="vm:CodeEditorViewModel"> <views:CodeEditorView /> </DataTemplate> <DataTemplate DataType="vm:BoardViewModel"> <board:BoardView /> </DataTemplate> </ContentControl.ContentTemplate> </ContentControl>
Плюсы
Не нужно менять VM. Авалонский DataTemplate сам матчит DataType. ActiveView — единый источник истины.
Минусы
Каждый DataTemplate должен быть зарегистрирован. Если view не находит шаблон — покажет текстовое представление типа.
Variant B Direct binding via RouteConverter
Один конвертер из маршрута в DataTemplate. Убирает EqualityConverter и множественные IsVisible.
public sealed class RouteToTemplateConverter : IValueConverter { public static readonly RouteToTemplateConverter Instance = new(); private readonly IDictionary<string, DataTemplate> _map; public RouteToTemplateConverter() { _map = new Dictionary<string, DataTemplate> { ["chat"] = (DataTemplate)Application.Current.Resources["ChatTemplate"], ["code"] = (DataTemplate)Application.Current.Resources["CodeTemplate"], ["board"] = (DataTemplate)Application.Current.Resources["BoardTemplate"], }; } public object? Convert(object? value, Type targetType, object? parameter, CultureInfo culture) => value is string s && _map.TryGetValue(s, out var tpl) ? tpl : null; public object? ConvertBack(...) => throw new NotSupportedException(); }
<!-- MainWindow.axaml --> <ContentControl Content="{Binding ActiveView}" ContentTemplate="{Binding ActiveView, Converter={StaticResource RouteToTemplateConv}}" />
Плюсы
Единый ContentControl вместо трёх sibling-views. Убирает IsVisible гонки.
Минусы
Нужно хранить шаблоны в Resources. Менее декларативно, чем DataTemplate с DataType.
Variant C View-specific properties (ContentControl.Content + ViewModelLocator)
Каждая view регистрирует фабрику в IViewModelLocator и поднимает свои typed properties.
// ChatView.axaml.cs public partial class ChatView : UserControl { public static readonly DependencyProperty ViewModelProperty = AvaloniaProperty.Register<ChatView, ChatViewModel>(nameof(ViewModel)); public ChatViewModel ViewModel { get => ( ChatViewModel )GetValue(ViewModelProperty); set => SetValue(ViewModelProperty, value); } public ChatView() { InitializeComponent(); DataContext = ViewModel; } }
<!-- MainWindow.axaml --> <views:ChatView ViewModel="{Binding Chat}" /> <views:CodeEditorView ViewModel="{Binding CodeEditor}" />
Плюсы
Явный typed binding. Локатор может резолвить view по VM через IViewModelLocator.Get<T>(). Идеально для plugin-driven UI.
Минусы
Требует DependencyProperty на каждой view. Много boilerplate. Конфликтует с MVVM Toolkit, который генерирует [ObservableProperty] для VM, но не для View.

Критерий IContentHost (AvaloniaContentHost) IViewModelLocator (ViewModelLocator) IServiceProvider (ServiceLocator anti-pattern)
Гранулярность Coarse: агрегирует фиксированный набор shell VMs Fine: резолвит любой зарегистрированный T по типу Fine: резолвит любой зарегистрированный T по типу
Точка входа Один объект IContentHost, внедряется в MainViewModel Singleton, резолвится где угодно через sp.GetRequiredService<IViewModelLocator>() Распространён через конструкторы/свойства
Производительность O(1): все VMs создаются один раз при построении хоста O(1) после первого вызова: кеш ConcurrentDictionary<Type, Func<IServiceProvider, object?>> O(log n) в худшем случае: reflection-based GetService
Время жизни Привязан к lifetime хоста (Singleton) Singleton с кешем делегатов Scoped/Singleton/Transient в зависимости от регистрации
Прозрачность Высокая: список VM виден в конструкторе AvaloniaContentHost Средняя: резолв происходит по строке имени типа Низкая: «магическая строка», нет compile-time проверки
Тестируемость Средняя: нужно мокать IContentHost Высокая: IViewModelLocator легко мокать Низкая: tight coupling к IServiceProvider
AOT-совместимость Да: прямой конструкторный инжект Да: кеш делегатов строится через expression trees Да, но reflection на hot path запрещён политиками
DI cycle risk Низкий: фиксированный набор, CommandPalette исключён Средний: Get<T>() может вызвать cycle при неправильной регистрации Высокий: скрытые зависимости, сложно отлаживать
Рекомендация Shell navigation — агрегирует known VMs Dynamic resolution — plugins, dialogs, overlays Избегать — использовать IViewModelLocator
ServiceLocator anti-pattern
Прямое использование IServiceProvider в view code-behind (старый подход) создаёт hidden coupling и ломает AOT. Все резолвы должны проходить через IViewModelLocator или конструкторный инжект.

warn 7. CommandPaletteViewModel — исключён намеренно

CommandPaletteViewModel не входит в AvaloniaContentHost. Причина — DI cycle:

  1. MainViewModel → (конструктор) → AvaloniaContentHost.
  2. AvaloniaContentHost → (конструктор) → CommandPaletteViewModel.
  3. CommandPaletteViewModel → (base class) → требует MainViewModel (через конструктор или callback).
  4. Цикл замкнут: DI не может построить граф.
Решение
MainViewModel держит Lazy<CommandPaletteViewModel>. Лямбда _commandPalette.Value вызывается только при открытии palette, после того как DI-контейнер полностью построен. Это разрывает цикл без изменения lifetimes.
// MainViewModel.cs private readonly Lazy<CommandPaletteViewModel> _commandPalette; public CommandPaletteViewModel CommandPalette => _commandPalette.Value;
Альтернатива
Можно было бы зарегистрировать CommandPaletteViewModel как Transient и внедрять Func<CommandPaletteViewModel>, но Lazy<T> дешевле: фабричный делегат строится один раз, а не на каждый вызов.

Когда использовать ContentHost

  • Фиксированный набор shell views (Chat, Code, Board).
  • Навигация по enum/route строке.
  • MainViewModel должен держать ссылки на все VMs.

Когда использовать ViewModelLocator

  • Динамические overlays (ProviderBrowser, Settings).
  • Plugin-resolved views.
  • Dialogs, которые создаются на лету.
  • Код-behind, который не имеет конструкторного инжекта.
